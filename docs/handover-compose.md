# 引継ぎ: 自動作曲の「キャッチーさ」について

2026-09-16〜18 のセッションの結論と、次にやることをまとめる。
**同じ調査を繰り返さないために読む。**

## 1行でいうと

**統計を参考コーパスへ寄せる方針は打ち止め。** 目標は「ヒット曲」ではなく
「人が手を入れる出発点」に置き直した。

## 何が分かっているか（すべて実測）

### 統計はキャッチーさを分けない

生成物と参考コーパス（`Music/_own/自作/界隈曲` 91本）は、次がすべて一致していた。

- `scripts/compare-corpus.ts` の17指標
- **隣接音程のヒストグラム**（0度 16.5/14.1、1度 10.5/14.5、2度 34.9/36.2 …）
- 反復（`compare-repetition.ts`）はむしろ生成物の方が多い
- `compare-reach.ts` の到達率 75%

それでいて所有者の評価は **コーパス約90%がキャッチー / 生成物 0/10**。

**分布が一致して知覚が完全に分離するなら、差は分布ではなく並び順にある。**
距離を目標にする方式ではこの情報は原理的に入らない。

### 目隠し聴取テストは有効だった

`tmp/blind.ts`。人間（他人の曲）と生成物を、伴奏なし・同じ音色・同じテンポ・
ラベル隠しで混ぜる。**12/13 で分離した**（判断を下した8件中7件正解＋5件中5件正解。
「判断が難しい」と言われた4件は全部生成物だった）。

差はメロディの音符列の中にある、と言ってよい。

**実施上の注意:**
- **1回5本まで。** 24本送ったとき、後半12本は聴かれなかった
- **人間側は他人の曲を使う。** 自作は聞き馴染みが交絡する（最初の版はこれで無効になった）
- 評価用サンプルは**全トラック入り**で出す。メロディ単体では判断が難しい

### 指標を新しく思いついたら

まず「これはキャッチーな曲とそうでない曲を**分けるか**」を問う。
これまでの指標は1つも分けていない。到達率（reach）は「その作風の曲を作れるか」で
あって「良い曲か」ではない。**品質の代理にしないこと。**

## 今どこで止まっているか

### 方針B（モデルで並び順を学ぶ）— 事前学習まで済んだ

`tools/melody-model/`（`tokenizer.py` / `train.py` / `generate.py` / `README.md`）。
手順は `tools/melody-model/README.md`。**残っているのは耳での選別（手順4）だけ。**

事前学習のコーパスは **PDMX**（作風・権利の両面で Lakh より適していることは実測済み。
9項目中6項目で界隈曲に近い。特に順次進行 0.512 対 0.278。`docs/dataset-provenance.md`）。

| | |
|---|---|
| 素材 | PDMX v9 `mid.tar.gz` の MIDI 254,035本 → 主旋律が取れた **186,774曲 / 音 3,689万** |
| トークン | **117,897,237**（91本は 99,238 だったので約1,190倍）。往復100%で欠落なし |
| 事前学習 | 60,000ステップ / 検証損失 **0.479**。学習側とほぼ同値で、暗記へ寄っていない |
| 微調整（91本） | lr 1e-4 で **25ステップが最良**（検証 0.535）。そこから先は上がる一方 |

**事前学習は効いた。** 界隈曲の同じ検証データで比べて、ゼロから学習 1.223 →
事前学習のみ 0.580 → 微調整後 0.535。

**微調整の効きは小さい**（0.580 → 0.535）。91本は事前学習の1/1000以下しかないので、
数十ステップで暗記側へ入る。`--eval-every` を刻んで最良点を拾うこと。

生成も済んでいる。2000本引いて候補 19,969種、そこから `weight` 比例で801種を抽出して
`src/compose-melodies.ts`（116KB。人間側の `compose-phrases.ts` は801種・111KB）。
**上位から切ると休符が落ちる**ので比例抽出にした（休符を含む割合は人間 78% /
候補全体 62% / 上位801種 42% / 比例抽出 55%）。

### 手順4「耳で選ぶ」は実行できない——バンク単位の A/B へ変えた

README の旧・手順4は「生成したフレーズを耳で選ぶ／**このコストは1回きり**」だったが、
**算数が合っていなかった**。同梱ぶん801種でも、実測の聴取能力（1回5本）では160回。
そのうえ判断の形式も無効で、伴奏なしのメロディ単体では判断が難しいと同じ実測で
分かっている（下記「目隠し聴取テスト」）。2小節の断片はもっと短い。

代わりに `tmp/ab-bank.ts`。同じ曲を素材だけ入れ替えて2本出し、**5組10本・約3分**で
「モデル製のバンクを採るか」だけを決める。`drawCount: 1` で引くのが肝で、既定の
40本引き＋選抜のままだと素材を変えた時点で勝つ候補が入れ替わり、テンポも進行も
別の曲になる（実測で5組すべて別物）。ドラムと楽器も曲調連動で変わるのでペア内で固定。

**結果: 差が無かった。** 5組10本の目隠し A/B で「どっちも似たようなもん」。
`src/compose-melodies.ts` は同梱せず削除した（バンク自体は `tmp/compose-melodies.ts`
に19,969種、モデルは `tmp/base.pt` / `tmp/melody-model.pt` に残っている）。

### ここから言えること（B-1 の結論）

素材を3通り試して、3回とも耳に届かなかった。

| 素材 | 結果 |
|---|---|
| 統計を参考コーパスへ寄せた旋律 | 17指標も隣接音程も一致して 0/10 |
| **人間の曲から抜いた実在の2小節** | 「良くなっていない」 |
| **1.18億トークンで事前学習したモデル製の2小節** | 人間の実在フレーズと**区別がつかない** |

**人間が書いた本物の2小節を使っても差が出ない**のだから、2小節という単位に
キャッチーさは載っていない。目隠し聴取テストで12/13が分離したのは**曲まるごとの
旋律**で、その差は2小節へ切った時点で失われている、と読むのが筋が通る。

つまり効いていないのは素材の作り方ではなく、**2小節へ切って引き直す枠組み**そのもの。
モデルは任意長の旋律を学んだのに、`generate.py` はそれを2小節へ刻んでいる——
学ばせた「並び順」のうち2小節を超えるぶんを捨てている。

### まるごと書かせても差が無かった（2026-09-19・4つめ）

`tmp/ab-whole.ts`。モデルに2小節へ刻まず旋律を書かせ、その曲の音階・調へ写して
同じ編曲へ差し込んだ（伴奏・ベース・パッド・コード・ドラム・テンポ・音色・小節数は
同一。ハモリは主旋律から導くので両方とも外した）。**結果は「差がない」。**

## 旋律の音符列を変える方向は打ち止め

4通り試して4回とも耳に届かなかった。

| 変えたもの | 結果 |
|---|---|
| 統計を参考コーパスへ寄せる | 17指標も隣接音程も一致して 0/10 |
| 人間の曲から抜いた**実在の2小節** | 「良くなっていない」 |
| 事前学習したモデル製の2小節 | 人間の実在フレーズと**区別がつかない** |
| モデルが**刻まずに書いた旋律まるごと** | 今の作曲の旋律と**差がない** |

**人間が書いた本物の旋律素材を使っても差が出ない。** ここから先「別のコーパス・
別のモデル・別の選抜」を試すのは、この4連敗の5本目になる。やらないこと。

**ただし「旋律は無関係」とまでは言えない。** 目隠し聴取テストでは人間の旋律と
生成物が12/13で分離している。分離するのに差し替えても変わらないなら、**この配線を
通した時点で旋律の違いが埋もれている**という読みが残る（音域の写し方・8小節の切り
出し・和音への合わせ・ハモリ無し・伴奏の厚み）。旋律そのものを疑う前に、旋律が
通っていく道を疑うほうが筋が通る。

## 残っている筋

旋律の外側。目標は「人が手を入れる出発点」（`compose-goal-is-editing-starting-point`）
なので、価値は引き直しと編集の側にある。

- **引き直しUX の残り**（下記）。スマホで「たくさん引いて選ぶ」を成立させる設計
- 編曲・音色・構成・歌詞の側。ここは一度も測っていない

学習パイプライン（`tools/melody-model/`）はそのまま残す。**結論は否定的だが配線と
実測値は揃っている**ので、旋律の外側を変えたあとで効き方が変わるなら再利用できる。

### 引き直しUXの残り

スマホ前提で「たくさん引いて選ぶ」を成立させる設計。候補を並べるUIは成立しない
（試聴時間・画面・生成コスト・AudioContext の resume 摩擦）。実装済みは3点で、
残りの案は `compose-goal-is-editing-starting-point` のメモにある。
