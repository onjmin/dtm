# 引継ぎ: 自動作曲の「キャッチーさ」について

2026-09-16〜18 のセッションの結論と、次にやることをまとめる。
**同じ調査を繰り返さないために読む。**

## 1行でいうと

**統計を参考コーパスへ寄せる方針は打ち止め。** 目標は「ヒット曲」ではなく
「人が手を入れる出発点」に置き直した。

## 何が分かっているか（すべて実測）

### 統計はキャッチーさを分けない

生成物と参考コーパス（`Music/_own/自作/界隈曲` 91本）は、次がすべて一致していた。

- `scripts/corpus/compare-corpus.ts` の17指標
- **隣接音程のヒストグラム**（0度 16.5/14.1、1度 10.5/14.5、2度 34.9/36.2 …）
- 反復（`compare-repetition.ts`）はむしろ生成物の方が多い
- `compare-reach.ts` の到達率 75%

それでいて所有者の評価は **コーパス約90%がキャッチー / 生成物 0/10**。

**分布が一致して知覚が完全に分離するなら、差は分布ではなく並び順にある。**
距離を目標にする方式ではこの情報は原理的に入らない。

### 目隠し聴取テストは有効だった

`tmp/blind.ts`。人間（他人の曲）と生成物を、伴奏なし・同じ音色・同じテンポ・
ラベル隠しで混ぜる。**12/13 で分離した**（判断を下した8件中7件正解＋5件中5件正解。
「判断が難しい」と言われた4件は全部生成物だった）。

差はメロディの音符列の中にある、と言ってよい。

**実施上の注意:**
- **1回5本まで。** 24本送ったとき、後半12本は聴かれなかった
- **人間側は他人の曲を使う。** 自作は聞き馴染みが交絡する（最初の版はこれで無効になった）
- 評価用サンプルは**全トラック入り**で出す。メロディ単体では判断が難しい

### 指標を新しく思いついたら

まず「これはキャッチーな曲とそうでない曲を**分けるか**」を問う。
これまでの指標は1つも分けていない。到達率（reach）は「その作風の曲を作れるか」で
あって「良い曲か」ではない。**品質の代理にしないこと。**

**算数が合っていなかった**。同梱ぶん801種でも、実測の聴取能力（1回5本）では160回。
そのうえ判断の形式も無効で、伴奏なしのメロディ単体では判断が難しいと同じ実測で

代わりに `tmp/ab-bank.ts`。同じ曲を素材だけ入れ替えて2本出し、**5組10本・約3分**で

40本引き＋選抜のままだと素材を変えた時点で勝つ候補が入れ替わり、テンポも進行も
別の曲になる（実測で5組すべて別物）。ドラムと楽器も曲調連動で変わるのでペア内で固定。

**結果: 差が無かった。** 5組10本の目隠し A/B で「どっちも似たようなもん」。
`src/compose-melodies.ts` は同梱せず削除した（バンク自体は `tmp/compose-melodies.ts`
に19,969種、モデルは `tmp/base.pt` / `tmp/melody-model.pt` に残っている）。

### ここから言えること（B-1 の結論）

素材を3通り試して、3回とも耳に届かなかった。

| 素材 | 結果 |
|---|---|
| 統計を参考コーパスへ寄せた旋律 | 17指標も隣接音程も一致して 0/10 |
| **人間の曲から抜いた実在の2小節** | 「良くなっていない」 |
| **1.18億トークンで事前学習したモデル製の2小節** | 人間の実在フレーズと**区別がつかない** |

**人間が書いた本物の2小節を使っても差が出ない**のだから、2小節という単位に
キャッチーさは載っていない。目隠し聴取テストで12/13が分離したのは**曲まるごとの
旋律**で、その差は2小節へ切った時点で失われている、と読むのが筋が通る。

つまり効いていないのは素材の作り方ではなく、**2小節へ切って引き直す枠組み**そのもの。
モデルは任意長の旋律を学んだのに、`generate.py` はそれを2小節へ刻んでいる——
学ばせた「並び順」のうち2小節を超えるぶんを捨てている。

### まるごと書かせても差が無かった（2026-09-19・4つめ）

`tmp/ab-whole.ts`。モデルに2小節へ刻まず旋律を書かせ、その曲の音階・調へ写して
同じ編曲へ差し込んだ（伴奏・ベース・パッド・コード・ドラム・テンポ・音色・小節数は
同一。ハモリは主旋律から導くので両方とも外した）。**結果は「差がない」。**

## 旋律の音符列を変える方向は打ち止め

4通り試して4回とも耳に届かなかった。

| 変えたもの | 結果 |
|---|---|
| 統計を参考コーパスへ寄せる | 17指標も隣接音程も一致して 0/10 |
| 人間の曲から抜いた**実在の2小節** | 「良くなっていない」 |
| 事前学習したモデル製の2小節 | 人間の実在フレーズと**区別がつかない** |
| モデルが**刻まずに書いた旋律まるごと** | 今の作曲の旋律と**差がない** |

**人間が書いた本物の旋律素材を使っても差が出ない。** ここから先「別のコーパス・
別のモデル・別の選抜」を試すのは、この4連敗の5本目になる。やらないこと。

**ただし「旋律は無関係」とまでは言えない。** 目隠し聴取テストでは人間の旋律と
生成物が12/13で分離している。分離するのに差し替えても変わらないなら、**この配線を
通した時点で旋律の違いが埋もれている**という読みが残る（音域の写し方・8小節の切り
出し・和音への合わせ・ハモリ無し・伴奏の厚み）。旋律そのものを疑う前に、旋律が
通っていく道を疑うほうが筋が通る。

## 2026-09-19 追記: 4連敗の測定器が未検証だった

上の表の後半2回（モデル製の2小節・モデルの旋律まるごと）は、`tmp/ab-bank.ts` /
`tmp/ab-whole.ts` の形式——**サビ8小節・全トラック入り・素材だけ差し替え**——で
測っている。この形式が「本当に違うもの」を違うと言えるかは、**一度も確かめていない。**

唯一シグナルが出た測定は目隠し聴取テスト（24小節・伴奏なし・人間対生成）の 12/13 で、
A/B とは長さと伴奏の有無の2点が違う。

### 分かったこと1: 旋律は別の曲のコード進行には載らない

`ab-whole.ts` の10本を、歌がコード＋ベースにどれだけ乗っているかで測り直した
（音価重み。「和音内」＝鳴っている和音の構成音、「衝突」＝和音外で構成音と半音でぶつかる）。

| 組 | A（今の作曲） | B（モデルの旋律まるごと） |
|---|---|---|
| 1 | 和音内 41% / 衝突 11% | 16% / 8% |
| 2 | 61% / 16% | 41% / 30% |
| 3 | 37% / 8% | 29% / 18% |
| 4 | 73% / 2% | 53% / 2% |
| 5 | 35% / 38% | 42% / 33% |

B は5組中4組で和音内が低く、3組で衝突が多い。**A の旋律はそのコード進行と一緒に
生成されたもので、B はよそのコード進行へ後から載せたもの**なのだから当然で、
「差がない」という判定は、噛み合った A と手枷つきの B を比べた結果だった。
これは「旋律は効かない」の根拠にならない。人間の旋律で同じことをしても同じ
（所有者の指摘「不協和音になっている」。移調量を伴奏に当てて選び直しても衝突は
減らなかった＝移調の問題ではなく素材とコードの対応の問題）。

**この配線で旋律だけを差し替える実験は、素材が何であれ成立しない。** 差し替える
なら和声も一緒に差し替える（再ハーモナイズ）か、伴奏を外す。

### 分かったこと2: 人間側の素材は「所有者が知らない曲」でなければならない

他作フォルダ `it_is_used` の旋律を出したら、所有者が1本を「よく覚えてる」と言った。
知っている旋律は「ましか」の判定に使えない。自作を外すだけでは足りない。
以後の人間側は **PDMX**（`tmp/pdmx.jsonl`、18万曲のパブリックドメイン譜面）から
無作為に引く。作風は界隈曲と完全には重ならないことは覚えておく（`docs/dataset-provenance.md`）。
なお 12/13 の目隠しテストも人間側が `it_is_used` だったなら、「人間か機械か」の
判別に聞き覚えが混ざっていた可能性は残る。

### 分かったこと3: 歌だけでは「ましか」を判定できない

伴奏を外した版（8小節・ピアノ）を出したら「メロディライン単体で聴いても判断しづらい」。
`ab-listening-budget` の実測どおり。**良否の判定には全トラックが要る**が、旋律だけを
差し替えると上記1で成立しない。両立させるには**A・B の両方に和声を付け直す**しかない。

### 陽性対照: `scripts/compose/ab-listen.ts`

`tmp/ab-whole.ts` の後継で、`scripts/` へ移して残した。B に**人間の本物の旋律**（PDMX）を
入れ、**A・B とも同じ手続きで和声を付け直して**全トラックで鳴らす。

```
npx tsx scripts/compose/ab-listen.ts --pdmx tmp/pdmx.jsonl --out tmp/ab-pdmx
```

手続き: 元の進行の小節割りを単位にし、調のダイアトニック三和音を候補に「和音内の音価−衝突」
と進行の常套（V→I、IV→V、同じ和音の連続を軽く嫌う）を Viterbi で解く。コードは曲と同じ
奏法、ベースは曲のベースのリズムと根音からの度数を保って新しい根音へ、パッドは時刻を
保って最寄りの構成音へ写す。サブメロとハモリは主旋律から導かれる声部なので両方とも外す。
ハーモナイザの出来は A・B に等しく効くので、独立変数は旋律だけに戻る。

付け直し後の当たり具合（音価重み）。A も元の進行より乗りが良くなっている点に注意——
**今の作曲は、自分で出した進行に自分の旋律が半分しか乗っていない**（後述）。

| 組 | A（今の作曲の旋律） | B（PDMX の旋律） |
|---|---|---|
| 1 | 和音内 63% / 衝突 9% | 81% / 13% |
| 2 | 50% / 11% | 60% / 10% |
| 3 | 78% / 15% | 75% / 6% |
| 4 | 41% / 11% | 84% / 6% |
| 5 | 45% / 3% | 47% / 10% |

### 分かったこと4: 出荷版そのものを対照に置いていなかった

ここまでの A/B は全部「試作 対 人間」で、**main で出荷している出力そのもの**（12本引き＋
選抜・ハモリ・2声・オクターブ重ね・サブメロ・自前の進行・楽器プリセット）は一度も
並んでいなかった（所有者の指摘）。`--release` で1曲につき3本出す。

```
npx tsx scripts/compose/ab-listen.ts --pdmx tmp/pdmx.jsonl --release --out tmp/abc-release
```

| | 中身 | 何が分かるか |
|---|---|---|
| A | 出荷版そのまま（`export-samples.ts` と同じ書き出し。オクターブ重ねだけアプリと同じく1オクターブ下げ） | 基準 |
| B | 同じ曲の同じ旋律を、和声付け直し（ハモリ・サブメロ無し）に通したもの | A−B ＝ **道具の損失** |
| C | PDMX の人間の旋律を、同じ和声付け直しに通したもの | B−C ＝ **旋律の差** |

A≈B が確かめられて初めて、A 対 C を「出荷版 対 人間」と読める。3本とも同じ曲・テンポ・
ドラム・楽器で、順番は組ごとに無作為。

**`tmp/abc-release/` に5組15本。** 答えは `_key.txt`。訊くのは「1・2・3 のどれがましか
（順位）」の1問だけ。15本は予算（10本）を超えるので、**3組目まででも成立する**——
組ごとに3本そろっていれば途中で止めてよい。

| 結果 | 読み |
|---|---|
| A≈B、C が勝つ | 道具は忠実で、人間の旋律は出荷版より良い。旋律の道は閉じない |
| A≈B、差なし | 8小節・目隠しでは「ましか」が決まらない。`--bars 24` へ |
| A≫B | 付け直しか声部の削減が聴感を落としている。B 対 C は読めるが A 対 C は読めない。道具側を直す |
| A≫C だが B≈C | ハモリ・サブメロ・自前の進行の側に価値がある＝旋律の外側が効いている |

`tmp/ab-pdmx/` は A/B 版（出荷版なし）。参考として残す。

#### 結果（2026-09-19、所有者の順位付け）

| 組 | 順位 |
|---|---|
| 1 | C > A > B |
| 2 | B > C > A |
| 3 | A > B > C |
| 4 | B > C > A |
| 5 | A > B > C |

対にすると A 対 B は 3-2、B 対 C は 4-1、A 対 C は 2-3。順位の合計は A 10 / B 9 / C 11。
5組では何も有意にならない（4-1 でも片側 p≈0.19）。読めるのは次の2点まで。

- **A≈B。** 和声の付け直しと声部の削減（ハモリ・サブメロ・自前の進行を外す）は
  聴感をはっきりとは落としていない。道具は出荷版に対して忠実と言ってよく、
  同時に**出荷版の「全部入り」は8小節の目隠しでは効いていない**。
- **C は勝っていない。** PDMX の人間の旋律は、同じ道具に通しても出荷版の旋律に

  作風が違う（賛美歌・古典・民謡の頂点8小節をJ-POP風のサビの位置に置いている。
  1組目の C は8小節で25音）ので「人間だから良い」が成り立たない素材だった、と
  読むのが自然。**形式の欠陥とは断定できない**が、形式が生きている証拠も得られなかった。

つまり **「旋律は効かない」は撤回も確定もできないまま**。人間の旋律で形式を検証するには
「所有者が知らない・作風が界隈曲に近い」素材が要り、手元には無い（自作は聞き馴染み、
他作 `it_is_used` も聞き馴染み、PDMX は作風違い）。

次の候補（どれも所有者の耳を使うので、着手前に確認する）:

1. **PDMX を作風で絞る**（1小節 6〜9 音・16分あり・音域 17 半音以内・4/4）。
   それでも「界隈の本物」ではない
2. **`--bars 24`** で長さを戻す（3組9本で約7分）。差が8小節より長い構造にあるという読みの検証
3. **耳による方式の採否はここで止め**、旋律の外側（編曲・音色・構成・歌詞・「合わせ方」）へ移る。
   A≈B が出たので、出荷版の全部入りも8小節では効いていない＝そこにも伸びしろがある

| 結果 | 読み | 次 |
|---|---|---|
| **人間が勝つ** | 成立する形式なら差は聞こえる。ab-whole の「差なし」は形式の欠陥（上記1）。旋律の道は閉じない | 同じ形式で `--model tmp/whole-melodies.jsonl`。モデルが人間に届くかを測り直す |
| **差がない** | 8小節・目隠しでは「ましか」が決まらない | `--bars 24` で長さを戻す。それでも差がなければ耳による方式の採否は打ち止め |

### ついでに見えたこと: 今の作曲の旋律はコードに半分しか乗っていない

`ab-whole.ts` の A（今の作曲そのまま）は和音内 35〜73%、半音衝突 2〜38%。上の表の
付け直し後でも 41〜78%。歌メロが構成音に乗る割合としては低い（B の PDMX は 60〜84%）。
`compose.ts` の旋律は和音を「重み」でしか見ていない（`CHORD_TONE_WEIGHT`・`toneWeight`）
ので、経過音・テンションが多くなる。**「メロディと伴奏の合わせ方」は旋律の外側の候補
として、陽性対照の結果と無関係に測る価値がある**（ただし数字を寄せるだけなら
`statistics-cannot-predict-catchiness` の二の舞。A/B で耳に問うこと）。

`tmp/abc-release/` は聴き終わった（上記）。撤回も確定もできず、素材の問題で止まっている。

### 旋律の外側・第1手: 和声だけを変える（`--variant chords`）

A/B/C で B が A に勝った2組は、**付け直しで和音内の割合が大きく上がった組**（38→64%、
49→59%）と一致していた。5組中2組なので弱いが、この一連の実験で唯一「何かと一致した」
信号。旋律を固定して和声だけを入れ替え、直接測る。

```

```

| | 中身 |
|---|---|
| A | 出荷版の旋律 ＋ 出荷版の進行・ベース・パッド（ハモリ・サブメロは和音から導く声部なので両方とも外す） |

訊くのは「1と2のどちらがましか」の1問だけ。

| 結果 | 次 |
|---|---|
| B が 4-1 以上 | 「旋律に和声を合わせる」が製品側のレバー。`compose.ts` の進行プールを旋律の後に再解決するか、`ComposeResult.chordProgression` の後処理として入れる。ハモリ・サブメロは新しい和音から引き直す |
| 差がない | 和音内の割合も耳には出ない。次は編曲（層の出し入れ）・音色（プリセット）・構成の順 |

**出荷版の進行は旋律に乗っていない**（この物差しで和音内 31〜62%、衝突 20〜32%。7th で
衝突が多めに出る物差しではある）。`compose.ts` は進行を先に引き、旋律は和音を「重み」でしか
見ないので、こうなる。

#### 結果（2026-09-19）: 差なし。和音内の割合は耳と一致しない

| 組 | 判定 | 和音内 A→B |
|---|---|---|
| 1 | A | 54→70% |
| 2 | 引き分け | 20→33% |
| 3 | A | 44→48% |
| 4 | 引き分け | 78→66% |
| 5 | B | 74→56% |

A 2 / B 1 / 引き分け 2。**和音内が最も上がった組で A が勝ち、A のほうが高い組で B が
勝った。** A/B/C で見えた「付け直しで和音内が上がった組が勝つ」は偶然だった。
「旋律に和声を合わせる」はレバーではない。出荷版の 7th 進行は、旋律に合わせた三和音に
少なくとも負けていない。

### この形式で差が出たものが一つも無い

| 変えたもの | 結果 |
|---|---|
| 旋律の素材（4通り） | 差なし |
| 全部入り（ハモリ・サブメロ・自前の進行）対 声部削減 | A≈B（3-2） |
| 人間（PDMX）の旋律 | 勝たず（1-4） |
| 和声だけ | 差なし（2-1-2） |

「全部本当に効かない」のか「8小節・目隠し・どちらがましか、という形式が何も聴き分けられ
ない」のかを、ここで切り分ける。**必ず聴き分けられるはずの差**を同じ形式で出して当てられる
かを見る（`--variant broken`。奇数組は旋律を見ずに無作為に引いた三和音、偶数組は伴奏だけ
三全音ずらし）。

```
npx tsx scripts/compose/ab-listen.ts --variant broken --seed 20260921 --out tmp/ab-broken
```

| 結果 | 読み |
|---|---|
| 壊した B が 5組とも負ける | 形式は生きている。上の「差なし」は本物で、8小節の聴感を動かすものが見つかっていない。次は編曲（層）・音色・構成 |
| 三全音は当たるが無作為三和音は当たらない | 形式は粗い差しか拾えない。細かい採否には使えない |
| 三全音も当たらない | 形式を捨てる。耳を使うなら曲まるごと・伴奏付き・別の質問（「どちらを直したいか」など）へ |

#### 結果（2026-09-19）: 三全音は当たり、無作為三和音は当たらない

| 組 | 壊し方 | 判定 |
|---|---|---|
| 1 | 無作為三和音 | A（出荷版）が勝ち |
| 2 | 三全音ずらし | A が勝ち |
| 3 | 無作為三和音 | **B（壊した側）が勝ち** |
| 4 | 三全音ずらし | A が勝ち（「不協和音」と指摘） |
| 5 | 無作為三和音（偶然協和） | 判定不能 |

三全音は 2/2 で当たる。無作為三和音は 1 勝 1 敗 1 不能で当たらない。**調の中の三和音なら、
旋律を見ずに引いた進行でも出荷版の進行と区別がつかない**。この形式（サビ8小節・目隠し・
「どちらがましか」）が拾えるのは、伴奏が調から外れる級の粗い差だけ。

### 結論: 8小節の目隠し A/B は細かい採否に使えない

旋律の素材（4通り）・声部の数・人間の旋律・和声の選び方は、どれもこの形式の分解能の下に
ある。**「全部効かない」のではなく「この測り方では何も見えない」**。ここから先、
同じ形式で編曲・音色・構成を測っても「差なし」が続くだけなので、**やらない**。

残る耳の使い道は、目標（`compose-goal-is-editing-starting-point`）に直接対応する問い。
「どちらがましか」ではなく、曲まるごとを聴いて**「これを出発点に手を入れるなら、どこを
直すか／ゼロから書くより速いか」**を訊く。これは採点ではなく仕様の聞き取りで、
1曲ずつでよく、目隠しも要らない。

`scripts/compose/ab-listen.ts` は残す（陽性対照・感度検査・和声付け直しの道具として再利用できる）。
`tmp/ab-*` `tmp/abc-*` は消えてよい。

### 次: 曲まるごとの聞き取り（採点ではなく仕様の聞き取り）

```
npx tsx scripts/compose/export-samples.ts --out tmp/interview --count 3 --seed 20260922
```

出荷版そのまま（`export-samples.ts`。オクターブ重ねをアプリと同じく1オクターブ下げるよう
直した）を3曲、まるごと。1曲ずつ聴いて `tmp/interview/_questions.md` の3問に答える。

1. **出発点として使うか**（この曲を土台に手を入れるか、捨ててゼロから書くか）
2. **最初に直す場所**（どのセクションの、どのトラックの、何）
3. **直す理由を一言**（つまらない／おかしい／足りない／多い、など）

判定は「ゼロから書くより速いか」（`compose-goal-is-editing-starting-point`）。ここで挙がる
「最初に直す場所」が、3曲で同じトラック・同じ種類に集中するなら、それが次に手を入れる
場所。散るなら、生成側ではなく引き直し・編集の側（UX）に価値があるという読みになる。

#### 結果（2026-09-19、所有者）

| 曲 | 出発点として | 最初に直す場所 | 理由 |
|---|---|---|---|
| 01 | 捨てる | （挙げられない） | — |
| 02 | 捨てる | （挙げられない） | — |
| 03 | 捨てる | （挙げられない） | — |

所有者の言葉: **「全曲耳に止めないし、インスピレーションの出発点にすらしない。曲にテーマが
なく、耳に訴えかけるようなメロディラインも感じられなかった」**。「最初に直す場所」は
具体的に挙げられない、との回答。

読めること:

- **「ゼロから書くより速いか」は 0/3 で否。** 目標（編集の出発点）に対しても現状は
  未達で、これは A/B の「差なし」とは違い、はっきりした信号。
- 直す場所が**トラックにもセクションにも落ちない**。「散った」のではなく「全体」。
  想定していた二分法（集中→生成側／散る→UX側）のどちらでもなく、**UX を磨いても
  拾えない**（拾う価値のある候補が出ていない）。引き直し UX の改善は、生成側が
  「たまに当たる」水準に達して初めて効く。
- 理由は**旋律の側**（テーマ・メロディライン）を指している。同日に「耳による旋律の採否は
  止めて外側へ」と決めたが、その決定の根拠だった 8小節 A/B は感度が無いと分かっている
  （`ab-8bar-blind-format-is-insensitive`）。**曲まるごとの聞き取りは 3曲で明確な反応が
  出た**ので、こちらが使える測定器。
- 「テーマ」は生成側で既に扱っている概念（フックの再現率・素材の使い回し率を参考曲へ
  合わせてある。`compose.ts` の restatement まわり）。**統計は合っているのに「テーマが無い」
  と聞こえる**——`statistics-cannot-predict-catchiness` と同じ構図で、参考曲へ数字を
  寄せる方向でこれを直すことはできない。

次の候補（着手前に所有者の判断が要る）:

1. **曲まるごとの聞き取りを測定器にして、旋律の作り方そのものを変える**（数字合わせでは
   なく方式を変える。例: サビの句を先に1つ決めて曲全体をそこから導く「フック先行」、
   または事前学習モデルにコード進行を条件付けして旋律をまるごと書かせる——以前の失敗は
   旋律をよその進行へ後から載せたことが原因で、条件付けはまだ試していない）。
   1回3曲・「捨てる／使う」の1問で回す。
2. **自動作曲の改善を止め**、カバー作り・打ち込みの側（3層のうち残り2つ）へ工数を移す。
   自動作曲は「ボタン1つで曲の形になる」機能として現状維持。

どちらも所有者の耳と時間を使うので、ここで止めて確認する。

### 所有者が「当たり」として貼った13曲（2026-09-19 に入手）

掲示板 https://unj-reze.onjmin.workers.dev/post/1318 に、所有者が**何百回か引いて気に入った
もの**を貼っている（13本、`tmp/liked/` に MML を落とした。MML は投稿の `mmlUrl` から取れる）。
これは**同じ生成器の出力から所有者の耳が選んだ集合**なので、参考コーパスと違って
「生成器の内側で何が当たりか」を直接比べられる。所有者のコメントも付いている
（「ゲーム音楽っぽい」「東方風」「戦闘曲っぽい」「荒ぶるメロディライン」「ﾋﾟﾛﾋﾟﾛの部分がいい」
「コード進行がエロい」）。

分かったこと（13本 対 現行生成器 300本の百分位。物差しは主旋律のみ）:

| 軸 | 当たり13本 | 読み |
|---|---|---|
| **当たり率** | 13 / 数百 ≈ **3〜5%** | 聞き取りの 0/3 はこの率と矛盾しない。生成器は「ゼロ」ではなく「たまに当たる」 |
| テンポ | 中央値 150（生成 136）。150以上が 8/13（生成 43%） | 速い側 |
| ドラム | dance / 16beat / disco **のみ**（4beat・8beat は 0/13、生成では 25%） | 前へ出る系だけ |
| 楽器 | piano / retro_game / acoustic のみ（12種のうち3種） | 所有者が手で選んでいる可能性あり |
| 同音連打率 | 中央値 p17（10/13 が p33 以下） | **同じ音を続けない旋律**を選んでいる。最も一貫した信号 |
| 16分の割合 | **二極**: 0（7/13、p0）か 0.27以上（6/13、p89〜p99） | 8分で組んだ旋律か、16分で走る旋律か。中間（たまに16分）は選ばれない |
| 音数/小節 | 「荒ぶる」は 9.5（p100）、「ゲーム音楽」は 7.0（p92） | 当たりの半分は生成器の分布の端にある |
| 制作時期 | 12/13 が 9/6〜9/10 の生成器 | 9/17〜18 の変更（フレーズバンク・指紋修正）後は 1本のみ |

現行と 9/10 時点（fe1d6a25）の生成器を同じ物差しで 200本ずつ比べると、分布はほぼ同じ。
違いは 16分の多い曲の出方（p90: 旧 0.33 → 新 0.19）と、休符率（旧 0.21 → 新 0.18）程度。
**当たりの半分が乗っている「16分で走る」領域が、新しい生成器ではやや出にくくなっている。**

読み:

- 所有者の耳が拾っているのは **J-POP の歌メロというよりゲーム BGM（東方系）の走り**。
  生成器は歌える音域・息継ぎ・16分の抑制で歌メロ側へ寄せているので、当たりは
  「抑制をすり抜けた端」に多い。当たり率が数%なのはそのため。
- `統計を寄せる` の二の舞にはしないこと。ここで言えるのは「所有者はこの領域を選ぶ」で、
  「この領域なら良い曲」ではない。同音連打の少なさ・16分の二極は**選ばれた側の特徴**で、
  そこへ全曲を寄せれば「全曲同じ顔」になる（`generator-fingerprint-invariants`）。
- 使い方として筋が通るのは、**利用者が選べる「ゲーム音楽風／インスト」の系統**を足すこと。
  テンポ 150〜185・dance/16beat/disco・16分の走り・歌の制約（音域・息継ぎ）を外す。
  雰囲気（`mood_*`）と同じ入口に置けば「全曲が寄る」ことにはならない。

### 種の埋め込み（2026-09-19 実装）

`composeSong` は `random` を差し替えれば決定的（検算済み）。アプリは作曲のたびに 32bit の種を
引いて `seededRandom(seed)`（compose.ts、mulberry32）を渡し、MML の先頭に
`#seed=<n> #compose=<テンプレート:調:音階:セクション>` を埋める（full / mini とも。読み込んだ
MML の宣言は引き継ぐ）。再現は

```
npx tsx scripts/compose/export-samples.ts --app-seed 3842857959 --compose custom:any:auto:intro-verse-prechorus-chorus
```

で、アプリの主旋律と**音符単位で一致**することを確かめた。これで所有者が今後貼る「当たり」は、
どの抽選から出たかを手元で再現でき、設定を変えた版と比べられる。上の13本は種が無い
（埋め込み前）ので、MML から特徴を測るしかない。

旋律の外側。目標は「人が手を入れる出発点」（`compose-goal-is-editing-starting-point`）
なので、価値は引き直しと編集の側にある。

- **引き直しUX の残り**（下記）。スマホで「たくさん引いて選ぶ」を成立させる設計
- 編曲・音色・構成・歌詞の側。ここは一度も測っていない

学習パイプライン（`scripts/melody-model/`）はそのまま残す。**結論は否定的だが配線と
実測値は揃っている**ので、旋律の外側を変えたあとで効き方が変わるなら再利用できる。

### 引き直しUXの残り

スマホ前提で「たくさん引いて選ぶ」を成立させる設計。候補を並べるUIは成立しない
（試聴時間・画面・生成コスト・AudioContext の resume 摩擦）。

2026-09-19 に3点足した（耳が要らない残件として着手）。

- **作曲したらそのまま鳴る。** 再生位置をサビの頭に置いてあるのに再生ボタンを待つと
  引き直し1回が2タップだった。作曲ボタンの押下がユーザー操作なので resume も通る
- **「呼び出す」→「入れ替え」。** 呼び出すだけだと今の曲が消えて A と B を行き来
  できなかった。今の曲をキープ枠へ入れてから取り出すので、もう一度押せば戻る。
  枠は1つのまま2曲の比較が成立する。取り出した曲もキープ時の再生位置（サビ）から鳴る
- **キープ枠は localStorage に残る**（`dtm-macro:kept`、MML と再生位置）。スマホでは
  別アプリを見て戻るとタブが再読み込みされるので、メモリだけだとそこで消えていた

副産物で見つけた**バグ**: 2.1.11 で書き出しに `#ver=` を足したとき読み込み側の宣言
リストに `ver` を足しておらず、`#ver=2.1.13` が本文に残って `v` `e` `r` が音符に
なり、**読み戻した曲の track 0 先頭に E の16分が1つ生えていた**（キープ→入れ替えで
MML が往復しないことから発覚）。`mml-parser.ts` の `META_DIRECTIVE` を直し、
`scripts/test/check-mml-meta.ts` が「宣言から音が生えない」ことを検算する。
**2.1.11〜2.1.13 で書き出した MML を読み込むと先頭に余計な音が入る**——手元の
ファイルを読み戻したら先頭の1音を疑うこと（修正後のパーサでは出ない）。

残りの案:

- 引き直しの単位を曲からセクションへ（サビだけ引き直す）。`composeSong` に seed が無く
  曲まるごとを引くので、部分引き直しは生成側の作り替えが要る。聞き取りで「最初に直す
  場所」が特定セクションに集中したら着手する価値がある
- 「入れ替え」で行き来した2曲のどちらを採るかを決めたあと、負けた側を消す操作は無い
  （キープ枠に残り続ける）。実害は無いので放置

### 第3版: 詠唱型（2026-09-30、同日）

所有者の判定（第2版の4本）: **「全然似てない。A は若干イントロのみ、以降化けの皮が剥がれる」。**
イントロ＝伴奏だけ（4つ打ち・8分オクターブのベース・7th の進行・ヤツメ穴型の刻み）は方向が合っていて、
**歌メロが入った瞬間に J-POP になる**。犯人は旋律の作り方（動機→セクエンツ→Bメロの駆け上がり→サビの
歌い上げ→終止形）と、サブメロ（ハモリ／対旋律）。界隈曲の歌メロ（ころんば系。所有者の耳コピ62曲）は
**1〜2小節の型（8分主体）を延々と繰り返す詠唱**で、音域は5度〜1オクターブ、順次と同音連打が主、型は和音に
合わせて動かさない（下で和音が2拍ごとに動き、ぶつかりも味）。伴奏には16分のアルペジオ（「ピロピロ」）が乗る。

#### 方式

- **`MelodyForm` に `"chant"`（詠唱）を足した**（`compose.ts`）。`ostinato` と同じ経路を通しつつ、
  セクションごとに型を持つ（source は `sourceOf` のまま。prechorus の a2 は a と同じ素材）。楽句は
  [問い＝素材, 答え＝その側の答え素材 ansA/ansB] を交互に置き、役割は全部 `motif`。2周目の素材
  （a2nd/b2nd・`useAlt`）・答えの変奏（`ANSWER_VARY`）・息継ぎ（`midBreath`・`breathBySection`）・
  Bメロのビルドアップ（`buildUpCell`・`run` 上書き）・サビの頂点（最終サビ2回目のフックを上端へ寄せる）・
  「一歩進んだ反復」（`repeatShift`）・小節またぎの食い（シンコペーションタイ）・大跳躍の折り返しは
  掛けない。`fitMotif` の maxShift 0、`preserveContour` は2和音小節でも真（型を和音に合わせない）、
  contour flat、`registerSpread` 0.1〜0.4、窓の幅 12+round(spread×5)＝13〜14半音、セクションの
  `registerShift` は掛けない（掛けると A＋サビで音域が1オクターブを超える）。平行調・同主調のセクションは
  窓を先に `keyShift` ぶん下げておく（音は後から +k されるので、放置するとCメロだけ窓の外＝19半音）。
  `headTension`・`chromaticAffinity`・`octaveAffinity` は抽選してから 0 に潰す（他の型の乱数列を変えないため）。
  楽句の2小節目は1小節目と同じ起点（`chantAnchor`）から輪郭を読む——既存の motif は小節ごとに和音の
  構成音へ起点を取り直すので、借りたフレーズが小節線で移調されて割れていた。
  セクション内の再現は確率ではなく決定的（同じ側の最初の楽句を毎回そのまま。答えの後半も写す。
  他セクションの答えは写さない）。着地は曲の最終小節だけ（`landing`）。役割は最後も `motif`
  （`cadence` にすると最後の2小節が終止形の書法で書き直される）。
  `pickPhrase` は詠唱＋8分グルーヴのとき16分入りの素材を ×0.3 に軽くする（コーパスの16分間隔は
  中央 0.027・p75 0.095——皆無ではないので外さない。×0.1 だと平均 0.010 で薄すぎた）。
  `"chant"` は `"auto"` では引かない（テンプレートか明示指定でだけ出る）。
- **`StructureTemplate.sub?: "arpeggio"`**：draw() のサブメロ抽選は従来どおり行って結果だけ捨て、
  進行の構成音（`buildChordPlacements` の `block` と同じ写像、bpm 120 固定）を **16分で上へ回す
  アルペジオを1オクターブ上・velocity 70** で `submelody` に入れる（全小節。イントロも）。3和音は上の
  根音で4音に埋めて1拍で一周（`arpSequence` と同じ）。ハモリ harmony/harmony2 は空。
  `arpeggio-fast` の配置をそのまま置かなかったのは、あれがストラム（6ステップずつ遅れて始まり重なる）で、
  サブメロトラックの単音前提（`checkVoice` の「単音」「重ならない」）を壊すため。構成音の集合は同じ。
- **kaiwai**：`form: "chant"`・`sub: "arpeggio"`。plans から prechorus を外した
  （[intro,verse,chorus,verse,chorus,bridge,chorus,chorus]×2 ／ [verse,chorus,verse,chorus,chorus] ／
  [intro,verse,chorus,verse,chorus]）。イントロの `barChoices` は 1→2（[2,2,4,4,8,8]）。
  **1小節のイントロは置けない**——compose の楽句は2小節単位（`unitOf(bar)=floor(bar/2)`）で、奇数長の
  セクションを挟むと以降の楽句が全部1小節ずれる。実測で1小節イントロの曲（seed 1/5/9/23/34/35）は歌が
  2小節目から始まり（bar1 が silent）、詠唱の4小節周期も和声の4小節から1小節ずれていた。可聴上は
  「歌の前に2小節」で同じ。既存テンプレートの `barChoices` に奇数は無い。
  2小節のイントロは `half` で2和音に詰めない（`room < 4` の素通し。詰めるには進行の3・4和音目が要るが
  `progression` は intro の2小節ぶんしか持たない）ので、`check-compose` の「イントロがサビの和音で始まる」
  は小節頭の比較から**和音の並び（平らに展開）の前方一致**へ変えた。
  それ以外（ドラム・ベース・進行・yonuki_minor・テンポ・楽器・伴奏の型）は第2版のまま。

### 骨格借用（第1段、2026-09-30）

所有者の決定: **「人力の耳コピはこの DAW の音で界隈曲に聴こえる」→ 音色は足りている。骨格借用で進める。**
`kaiwai` の第4版（伴奏側が「若干」）はそのまま残し、別テンプレート `kaiwai_skeleton`（「界隈曲（骨格借用）」）を足した。

#### 方式

- 所有者の耳コピ MIDI（`Music/_own/自作/界隈曲`、重複を除いて 62 曲。集め方は `measure-arrangement.ts` の
  `collectSongs` と同じ）から曲ごとの**骨格**を抜く: 半小節ごとの和音名（主音を短調なら A、長調なら C へ移調）、
  ベースのオンセットと「和音ルートからの半音差」、主旋律のリズム（192 ステップ）と度数（C4=0 の絶対度数）、
  反復の地図（`sameAs` / `rhythmSameAs`）、鳴っている層（arp/pad/counter/stab）、セクション、ドラム型、
  刻み、音域の中心、GM 音色。型は `src/compose/skeleton-types.ts`、データは `src/compose/compose-skeletons.ts`
  （自動生成 225KB、`SKELETON_CORPUS_SIZE = 62`）。抽出は `scripts/corpus/extract-skeletons.ts`（2.4 秒）。
- 生成（`src/compose/compose-skeleton.ts` の `composeSkeleton`）: 骨格を1つ引き、調だけ変え、和音・ベース・
  ドラム・arp/pad 層・セクションは骨格どおり。歌メロは骨格のリズムと反復の地図に沿って **他の曲の実在フレーズ**
  （`CORPUS_PHRASES`）の度数を当てる。`sameAs` 連鎖の先頭を写し（抽出は曲頭から探すのでセクションを跨ぐ:
  2番サビ＝1番サビ）、`rhythmSameAs` の小節は参照先と同じ度数列を避ける。強拍（小節頭・半小節頭）の音だけ
  その和音の構成音へ最寄りで寄せる。元曲の旋律の音は既定では使わない（`melodySource: "original"` は対照用）。
- 進行（`chordProgression`）は共通経路と同じく**基準調（ハ長調 / A マイナー）のまま**返し、調は `rootShift`。
  DAW・export-samples・measure-arrangement が `buildChordPlacements(chordProgression, rootShift)` で移調する。
- 共通経路との関係: `composeSong` の先頭で `template.engine === "skeleton"` なら乱数を1つも消費せずに分岐する
  （compose.ts :6010）。骨格の乱数の順は 骨格 → 調 → 楽器 → 楽句ごとのフレーズ → arp の形・強さ。

#### 統合で直した点

- ベースの音域の畳み込み（24〜60）を**移調後**に効かせる。基準調で畳んでから移調していたので rootShift +6 の曲で
  62 まで出ていた（seed 35）。ベースは移調後の実音で組み、他の層だけ最後に移調する。
- `anchorDegrees` の走査幅を -35〜98 度へ。`original` の絶対度数は元曲の音域そのまま（C2 付近なら -17 前後）で、
  旧走査（-21〜42）では持ち上げ切れず MIDI 43〜50 に落ちていた。`phrases` の結果は変わらない（近い候補が
  勝つ規則なので、下へ広げても選ばれない）。
- **主旋律の中心が C3（48）未満の骨格は引かない**（`MELODY_CENTER_MIN`）。62 本中 2 本
  （`闇の受験生/繰り返す繰り返す繰り返す` 中心 32、`まずま/8Weu4gs` 中心 37＝ch3「ベース」を最長被覆で採った）は
  「C3 以上の単旋律 ch が無い」曲で、抽出がベース音域の ch を主旋律にしていた。歌の設計図にならない。
- 検算 `validateSkeletons` を `skeleton-types.ts` へ移し、抽出（`--check`）とテスト（fixture・実データ）が同じ
  条件で通る。型コメントの食い違い（degrees は絶対度数で CORPUS_PHRASES の相対度数と違う、`melodyCenter` は
  生成側が移調後の実音の中心として読む）を直した。

#### 反証対応（第1段の直し、2026-09-30）

#### 方式

- **抽象骨格バンク** `src/compose/compose-section-bank.ts`（自動生成 128KB、`scripts/corpus/build-section-bank.ts`
  が手元の骨格データ `loadSkeletons()` から作り、書いた後に `biome format` を掛ける。再生成は byte 同一。型と符号化・
  検算は `src/compose/section-bank-types.ts`）。単位は**セクション**（60 曲 → 310 本: intro 38 / verse 77 / bridge 67 /
  chorus 74 / interlude 27 / outro 27）。長さは 4 の倍数に丸め（0 になる 13 本は落とす）、**歌わない種類
  （intro/interlude/outro）は 16 小節で頭打ち**（`NON_SUNG_MAX_BARS`。抽出が大きな後奏を 1 セクションにまとめた
  64〜72 小節の outro があり、そのまま構成に使うと歌 14 小節の 88 小節曲になった）。**donor の選別**
  （`donorRejection`）: 和音が 2 つ以下（3 本。置換は最初と最後の和音に掛けないので、`Gdim7 | F | 継続×14` のような
  サビは donor と同じ並びを縮められない）・最初／最後の和音が 12 半小節を超えて続く（0 本）・調外のルートが過半
  （8 本。抽出の和音名がクロマチックに付いた印）を落とす。
  持つのは kind・mode・bars・src（id 順の通し番号。曲名は `tmp/section-bank-map.json` にだけ置く）・和音名
  （Am/C 基準、null は継続）・**ベースの型の種類**（`classifyBass`: octave8 1344 / offbeat 260 / tresillo 249 /
  sustain 193 / fifthmix 177 / quarter 134 / root8 17 / dotted 4 / rest 290 / other 1084。offbeat（裏打ち）は仕様の

     継ぎ目で 10 半音以上跳んだ）。**転調するセクションの再現は 1 番と同じオクターブに乗せる**——窓の上端を
     転調ぶん下げ、帯への折り返しは 1 番とラスサビ両方の移調量で見る（`foldRangeAt`。直す前は 83 を超えた小節が

  7. 層: arp は**ラスサビの小節だけ**（donor の arp は見ない）、pad は donor どおり。ハモリ・オクターブ重ねは空。
