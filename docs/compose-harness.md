# 作曲ハーネス: 曲を作って渡すときの進め方

「自動作曲で曲を作って、自分で評価して納得したものを渡して（手で直してよい）」という依頼を、
**Opus 5.5 が手順と点検で品質を担保しながら進める**ための文書。
生成器そのもの（`src/compose/`）を直す作業は [handover-compose.md](handover-compose.md) の領分で、ここでは扱わない。

モデルの判断に任せると抜ける所を、手順・点検スクリプト・渡し方の型で埋めるのが狙い。
点検は3段に分ける。**関門**（流派の規則で確かめられるもの。不合格なら渡さない）、
**仮説**（2曲の比較から出たもの。所有者の評価で確かめるまで合否にしない）、**注意**（鳴らして決めるもの）。

## 1. なぜ要るか（2026-10-17 の比較）

同じ依頼で Opus 5.5（中）と Fable 5.1（高）が1曲ずつ作り、所有者は Fable の曲を上とした。
作り方（生成された伴奏の層を小節単位で写して組み直し、リードを手書き）は同じで、差は作り方の中の選択だった。
両セッションで突き合わせて合意した内容を下に置く。

| 確かめられた差 | Opus（`scratch/kw/`、Speder2） | Fable（`scratch/kw2/`、2号兄貴） |
|---|---|---|
| 和声の素材（半小節ごとの伴奏の音の組み合わせ） | 7 種。進行2つで88小節 | 15 種。サビ終わりの2-5・抜き専用・終止用を選んだ |
| 終わり方 | Ⅵのまま、リード無しで終わる | Ⅴ→ⅰ、主音の全音符 |
| Aとサビの対比 | 持ち上げ +4.5 半音、音の細かさほぼ同じ | +11.3 半音、Aは16分・サビは伸ばす |
| 短9度（旧い数え方） | 32 か所を「よくある響き」として残した | 0。拍頭の和音音 49% を見て書き直した |
| リードの占有率 | 67%（イントロ12小節・抜き8小節が無音） | 95% |
| 伴奏とリードの強さ | 伴奏（t8 エレピ 99）の平均ベロシティがリード（86）を上回る | リード 100、伴奏 60 前後 |

- **仮説**（1曲対1曲では切り分けられない）: 流派の選択（所有者の当たり13曲は速い・16分が多い）、ミックス、
  高域（Opus 版の t6 が高い E を全編持続、矩形波リードの音域）。
- **割り引くこと**: 流派・エフォート（中と高）・作った順（Fable は Opus の道具を読んでから始めた）・
  途中の所有者の指摘（Fable の曲は「高音が痛い」を受けて測り直した）が違う。
- 差のうち「持ち上げ」「音の細かさの対比」は Fable が選んだ書き方で、2号兄貴の規則（サビでも16分で走る）とはむしろ逆。
  ほかの流派へそのまま持ち込めない。だから点検では仮説に置く（§2 G4）。

**この比較で Opus が実際に抜かしたこと**:
- 生成器の出した構造（素材の少なさ）を、確かめずにそのまま曲の形にした。
- 数値で出た濁りを理屈で許した。
- メモリにある所有者の好みを読んだのに、選択の根拠に使わなかった。
- 再生がうまく動かないと、音での確認をそこで諦めた。
- 点検の数値を見て旋律を書き直す反復をしなかった（Fable は拍頭の和音音 49%→76%、短9度 2→0 まで回した）。

### 2026-10-18 の比較検証（このハーネスで作った曲の評価）

Opus 5.5 がこの手順で 2号 seed 3021 を手直しし、所有者は「サビが聴けるレベルで及第点」とした。
方式の効果か seed の良さかを切り分けるため、次の4本を目隠しで聴いてもらった（曲まるごと、使う／捨てる）。

| 曲 | 中身 | 関門 | 仮説 | 評価 |
|---|---|---|---|---|
| 基準 | 2号 3021・この手順で手直し | 合格 | 4/6 | 及第点（10-17） |
| C | 2号 3021・アプリの素の出力 | 16分 15% で不合格 | 3/6 | 捨てる |
| A | 2号 3021・生成器のリードのまま、並べ直しと音量だけ当てた | 16分 16% で不合格 | 2/6 | 捨てる |
| D | 2号 3027・この手順で手直し | 合格 | 5/6 | **使う**「メロディが伴奏と調和とれてた」 |
| B | Speder2 4008・この手順で手直し | 合格 | 5/5（素材は判定なし） | 捨てる |

基準と D の「Ⅴ→ⅰ」は、最後のサビで全音上へ転調したため `--key` の調で測ると外れる。転調後の調で測ると満たす。

- **並べ直しと音量だけでは足りない**（A）。効いたのはリードの書き方。
- 「調和」を測った（`scratch/cmp/harmony.ts`）。リードの発音時に鳴っている伴奏の音名と比べ、長さで重みづけた。
  - 手書きのリード（基準・D・B）: 伴奏と同じ音名 83〜94%、半音でこすれる 3%。
  - 生成器のリード（A・C）: 57〜59%、27%。生成器は和音名だけを見てリードを作るので、層が実際に鳴らす音（セブンス・テンション・調の外の和音）とこすれる。
- ただし B は調和が一番高い（94%・3%）のに捨てられた。調和は要るが、それだけでは足りない。B は遅い流派（122）でビブラフォンのリード、当たり集合の好み（速い・16分）から外れる。
- 仮説の段は評価を分けなかった（B は全部満たして捨てる）。関門へ上げる項目はまだ無い。

## 2. 手順

各段の成果物は作業フォルダ（`scratch/<名前>/`、git 管理外）に置く。段ごとに **何を見たか** を `notes.md` に1〜2行残す。

### G0. 読む

- [handover-compose.md](handover-compose.md) §0（カードの基準）・§2（やらないこと）
- [kaiwai-lineages.md](kaiwai-lineages.md) の該当流派（ゲームBGMなら [game-bgm-toby-fox.md](game-bgm-toby-fox.md)）
- メモリの所有者の評価（当たり集合・流派ごとの感想）。**流派・テンポを選んだ理由に書き込む。**

### G1. 流派と seed を選ぶ

- 流派は「所有者の好みの領域」と「依頼の言葉」の両方から選び、理由を `notes.md` に書く。
- seed の候補は代理の数値で絞る（2小節窓の再出率・ぶつかり・サビの持ち上げ・音域・占有。
  雛形は `scratch/kw/score.ts`）。**決め手は数値ではなく、小節ごとに全層を読むこと**
  （和音・リード・ベース・どの層がどこで鳴るか。雛形は `scratch/kw/dump.ts`・`act.ts`）。
- 和声の素材が流派の規則の範囲で足りる seed を選ぶ。`chordProgression` を小節ごとに読み、
  Aメロ・サビのループに加えて、**サビの終わりの形**（2-5 や属和音で次へ渡す小節）や抜き・アウトロに使える別の進行があるかを見る。
  Speder2 のように少数和音のループ自体が規則の流派では、種類の多さを求めない。

### G2. 曲の設計表を先に書く

音符を書く前に `notes.md` へ表を作る。列は「小節・部・進行（実音）・鳴らす層・リードの書法」。

- **借りる小節は和音名で照合してから写す。** 素材の和音が違えばビルドを止める（Fable の `scratch/kw2/build.ts` の `Mat.chords` と
  `song.chordProgression` の突き合わせ）。これは点検スクリプトでは拾えないので、組み直しのスクリプトに必ず入れる。
- 各部に「新しく聴くもの」（新しい進行か旋律）を持たせるか、流派の規則（ループの使い回し）に従うかを部ごとに決めて書く。
- 終わり方を決めて書く（Ⅴ→ⅰ で閉じる／ループで先頭へ戻る／ブロックの切れ目で切る）。流派の原曲の型から選ぶ。
- リードが出る小節を決める。流派の原曲に長い旋律なしイントロがある（Speder2・2号兄貴は 16 小節まで）なら、それを根拠にしてよい。
- 抜き（リードを外す部）やイントロの長さは、関門の占有率の帯を見て決める（2号兄貴は 70% 以上。80 小節の曲で抜き8小節＋旋律なしイントロ8小節なら 80% 前後まで下がる）。

### G3. リードを書き、点検の数値で書き直す

- **点検（G4）を回して、数値を見て旋律を書き直す反復を必ずする。** 1回書いて終わりにしない。
- 流派の規則の数値（16分・3連・音域・占有）を [kaiwai-lineages.md](kaiwai-lineages.md) と照合表にする。
- テーマはイントロの予告・Aメロ・アウトロで再現し、サビはテーマの形から作る。
- 「サビの4小節を全部同じ小節で埋めない」「頂点の音はサビで1回」は J-POP 向けの書き方（[handscore.md](handscore.md)）由来で、
  4小節ブロックを使い回す流派（2号兄貴 68%）とは相性が悪い。**流派の規則より優先しない。**
- 耳コピ由来の旋律・進行は使わない（[handover-compose.md](handover-compose.md) §0）。1曲の写しにしない。

### G4. 点検を通す

```
npx tsx scripts/compose/audit-arrangement.ts scratch/<名前>/song.mml --profile 2go --key Gm \
  --sections intro:8,A:16,B:16,break:8,A:8,B:16,outro:8
```

- `--profile` は `2go` / `speder2` / `kaisen` / `game` / `none`。部の名前は A で始まればAメロ、B で始まればサビ。
- **関門に不合格が1件でも残れば渡さない。** 直すか、その関門を外す理由を所有者に訊く（自分で例外にしない）。
- 仮説を満たさないときは、満たさない理由（流派の規則に従った等）を `notes.md` に書く。直すかは自分で決めてよい。
- 注意に出たものは G5 で測る。

| 段 | 項目 | 基準 | 出どころ |
|---|---|---|---|
| 関門 | テンポ・リードの16分・占有率・音域 | 流派ごとの帯 | 原曲の値（kaiwai-lineages.md・game-bgm-toby-fox.md）。根拠の曲数は 2号 8・Speder2 4・海鮮 5（完成 3）・ゲーム 13。Speder2 の帯は薄いので、落ちたら先に帯を疑う |
| 関門 | ぶつかり | 生成器の素の出力の p90 以下 | 下の較正 |
| 仮説 | 和声の素材 10 種以上（Speder2 は測らない） | | 2曲比較 |
| 仮説 | サビの持ち上げ +6 半音・Aとサビの発音間隔の比 1.2 | | 2曲比較（2号の規則とは逆向きになりうる） |
| 仮説 | A・サビ以外の部が新しい和声か旋律を持つ | | 2曲比較 |
| 仮説 | Ⅴ→ⅰ で終わる（ゲームは「主音で終わるか先頭へ戻れる」） | | 2曲比較 |
| 仮説 | リードが流派ごとの小節までに出る（2号・Speder2 は 16、ほかは 8） | | 2曲比較・原曲のイントロ長 |
| 注意 | 伴奏の平均ベロシティがリードを上回る・高い持続音・リードの最高音 84 以上 | | 聴いて決める |

**ぶつかりの数え方**: 8分以上のリード音について、拍頭で最低音と短2度・三全音になるもの、鳴っている伴奏の音の半音上（短9度）になるもの。
maj7 の上の根音（最低音と同じ音名のリード）と、属7（根・長3度・短7度）の上の ♭9・♯9 は流派の常套句なので数えない。
旧い数え方（2曲比較の表）ではこれらも数えていた。

**較正**（2026-10-17、`scripts/compose/calibrate-arrangement-gates.ts`、各テンプレート seed 1〜20 の素の出力）:

| | ぶつかり p50／p90（関門の上限） | 関門の不合格（20 曲中） |
|---|---|---|
| 2号兄貴 | 10%／18% | リードの16分 6・占有率 8・ぶつかり 2・音域 1 |
| Speder2 | 7%／20% | ぶつかり 3・占有率 2・テンポ 1 |
| 海鮮 | 6%／8% | ぶつかり 3 |
| ゲームBGM | 15%／22% | ぶつかり 2 |

- ぶつかりは上限を p90 に置いたので、素の出力の1割前後が落ちるのは設計どおり。
- **2号兄貴の素の出力が原曲の帯を外れる**（16分 30% 未満が 6/20、占有率 70% 未満が 8/20。原曲は 8/8 が 16分 30% 以上、占有 77〜93%）。
  関門の誤りではなく生成器の外れとみて帯は残した。生成器を直す側の課題（[handover-compose.md](handover-compose.md)）。
- 終わり方は関門にしなかった。2号・海鮮・Speder2 の原曲はブロックの切れ目で終わる曲が多く、ゲームBGM のループ判定は素の出力の 3 割を落とした。
- 2026-10-17 の2曲は、どちらも関門の不合格 0 件。差は仮説の段に出る（Opus 版は 4 項目を満たさず、Fable 版は全部満たす）。

### G5. 音で確かめる

譜面の点検が通っても、音量・高域は鳴らさないと分からない。所有者に渡す前に録音して測る（Fable が 2026-10-17 に実際に回した手順）。

1. ブラウザのプレビュー（`.claude/launch.json` の `dtm-demo`）で編集画面に `#g.…` を開く。
   **同じページでハッシュだけ変えても読み直さないので、`navigate` の後に `location.reload()` する**（空の曲を測りかけた例がある）。
2. `window.studio.startWavRecording()` → `await daw.play()` → 曲の長さだけ待つ → `await window.studio.stopWavRecording()`（WAV の Blob）。
   ブラウザの `javascript_tool` は 45 秒で切れるので、**録音〜解析は async で起動して結果を `window.__res` に入れ、別の呼び出しで取りに行く。**
3. Blob を `studio.audioContext.decodeAudioData` で読み、小節ごとに RMS（素の値と K 特性の近似: 38 Hz ハイパス＋1.5 kHz 以上 +4 dB の棚）・2〜6 kHz 帯・ピークを出す。
4. **全体だけでなくパート単独でも録る。** リードだけ（`@0`）・ベースだけ（`@4`/`@5`）・伴奏だけ（`@7`/`@8`/`@10` など）の MML を作って読み直し、同じ測定をする。
   見る所はパート間の差（リード単体で全体と同じ RMS なら、リード1本でリミッターが効いている）。
   ピークが −0.3 dBFS に張り付くのはリミッターが曲全体で効くためで、音源の正規化（e3562c10）の後も残る。それ自体は問題にしない。
5. 素の RMS を揃えても聴感は揃わなかった（2026-10-17 の結論）。比べるなら K 特性の値で。
6. 直す前後を所有者に聴き比べてもらうときは、両方の版を1枚の HTML にまとめて渡す（雛形 `scratch/kw2/make-ab.mjs`）。

再生位置が 0 から動かない・音が出ないときは、原因を追って直す（2026-10-17 の Opus 版では原因を追わずに諦めた）。
測れなかった場合は、測れなかったことを渡すときに書く。

### G6. 渡す

- 試聴は公開デモの埋め込み URL（`npx tsx scripts/misc/mml-embed-url.ts song.mml`）。localhost は所有者が閉じると聴けない。
  公開版の未デプロイの機能に頼るなら、先に push とデプロイを済ませる。
- 自己評価は「**確かめた差**（数値つき）」と「**仮説**」に分けて書く。聴けていないことは明記する。
- 所有者に訊くのは採点ではなく仕様: 「出発点として使うか／最初に直す場所／理由を一言」（[handover-compose.md](handover-compose.md) §2「試聴を頼むとき」）。1日5本まで。

## 3. 道具

| 道具 | 用途 |
|---|---|
| `scripts/compose/audit-arrangement.ts` | G4 の点検（関門・仮説・注意）。部ごとのリードの表・トラック表（音色・平均ベロシティ・リードとの重なり）も出す。`--json` で数値を書き出す |
| `scripts/compose/calibrate-arrangement-gates.ts` | 関門を生成器の素の出力に掛ける。**関門の閾値を動かしたら必ず回す**（素の出力を多く落とす関門は、流派に忠実な曲を落とす関門） |
| `scripts/compose/audit-lineage.ts` | 生成器の出力を流派の原曲と同じ物差しで点検（seed 選びの前の全体像） |
| `scripts/compose/export-samples.ts --app-seed` | アプリで作った曲の再現 |
| `scripts/misc/mml-embed-url.ts` | MML → 公開デモの埋め込み URL |
| `src/mml/mml-core.ts` の `MMLCore.getMMLFromNotes` | ノート列 → トラックの MML（アプリの書き出しと同じ） |

git 管理外の雛形（`scratch/`、消えることがある。使うならコピーして書き換える）:
`scratch/kw2/build.ts`（組み直し・和音名照合・手書きリード・ヘッダ）、`scratch/kw2/stats.ts`（部ごとの16分・3連・裏16分・占有・音域）、
`scratch/kw/score.ts`（seed の代理指標）、`scratch/kw/dump.ts`・`act.ts`（小節ごとの全層・層の出入り）、`scratch/kw2/make-ab.mjs`（聴き比べ HTML）。
長く使うことになったら `scripts/` へ写す（AGENTS.md の規則）。

アプリと同じ曲を seed から作るときは、ブラウザで `Math.random` の最初の1回だけを差し替えてから「作る」を押す
（`daw.ts` の `runCompose` は種を `Math.random` から1回引く）。MML の先頭の `#seed=` が狙った値かを必ず確かめる。

**おまかせマスタリングの扱い**: 作曲で作った層は `8d0bb142` 以降、作曲スロットから役割を引く。
**手で組んだ MML（スロット無し）は今も役割推定に掛かり**、単音のアルペジオや刻みは「サブメロ」（音量 92・Lead 6）と推定されうる。
手組みの曲は音量・音色・定位を自分で書く（Fable は役割別の `AUTO_ROLE_MIX` の値を写した）。

## 4. やらないこと

- 生成器の構造を、確かめずに曲の形として採る（素材が足りなければ seed を替える）。
- 関門の不合格を自分の判断で例外にする。
- 拍頭の和音音の割合を良し悪しの指標に使う（2曲比較で、どちらの評価とも対応しなかった）。
- 耳コピ由来の旋律・進行を素材にする。
- 2曲比較から出た仮説を、流派の規則より優先する。

## 5. 位置づけと限界

- 2曲比較で効いた差の一部（素材の選び方・終わり方・濁り・反復の有無）は手順で拾える種類だが、
  一部（持ち上げ・音の細かさの対比）は Fable の書き方の選択で、流派によっては規則と衝突する。
  **このハーネスが所有者の評価と一致するかは、まだ確かめていない。** 仮説の段は「仮説の関門」として扱う。
- 迷う所（流派の選択、関門を外すかの判断）は所有者に訊く。

## 6. この文書の更新
