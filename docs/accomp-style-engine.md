**実装の状況: 段階 S1 まで済み**（S0: `#compose` の書式・監査・`references/fb/`・黄金値・退避率の記録。S1: 表を `src/compose/accomp-styles/fb.ts` へ移し、エンジンはスタイルから読む・DAW は `song.mix` と層の定義を読む・計画の記録 `PlanPins`）。P-1・P-3・S2 以降は未着手。設計からずらした点は付録 F。

## 0. 1ページで

- **結論**: `composeAccomp` を「スタイルのデータを読む解釈器（スタイルエンジン）」に作り替える。fb はその最初のスタイル。
  - fb 系統の中の模倣先は、スタイルのデータを1つ足すだけで済むようにする。
  - 系統の外（短調の持続音・旋法・別の拍子など）は、最初の数本でエンジンに汎用の機能を足す（2つ目で約7機能・約2〜4日の見積もり）。
  - `composeSong`（歌メロが主役の J-POP）は触らない。3つ目のエンジンも作らない。
- **いま似る原因**は音高の選び方ではなく、1通りに固定されているもの（楽器とミックス、役割ごとの低音・和音のリズム、借用和音の小節の long、分散のセルと音域窓と密度、強弱の曲線と区間の並び、曲の頭と最終小節）。表を fb 1曲から起こしたので「スタイルの幅」を書いていない。
- **「似たものしか出ない」への答え**:
  - スタイルの中に**型（archetype）**を複数持つ。型＝ミックス・テンポ帯と長さ・強弱の曲線・並びの変種・層ごとの密度を一緒に設計した束（アレンジャーキーボードの Main A〜D）。1曲はまず型を引き、その中身を引く。
  - リズム・分散のセル・音域・密度を、役割ごとに1つから**エネルギー段ごとの表**（1段3行以上）にする。句の表も3行以上、借用の組は本当に別の和音の組にする。
  - 行は必ず所有者が**承認した**手書きの試作から起こす。既存の承認済み試作は行になり切っているので、表を広げる前に新しい試作を書く（P-3）。
  - ばらつきは**監査で測るが、測った値で曲を選ばない**（内蔵採点は構造品質と r = −0.06）。
- **「保守が面倒」への答え**:
  - エンジンにスタイル名・役割名・行 id を書かない（lint で0件を保つ。S3g で達成予定）。
  - 足りない機能は汎用の生成器か制約として、エンジンの検査付きで足す。スタイルごとの分岐は書かない。
  - 検査はエンジン用1本とスタイル用1本（全スタイルを同じコードで回す）。DAW と UI はスタイルを足しても変わらない。

## 1. いま似る理由（計測の要点）

生成48曲の組（GG）を手書きの基準（同じ曲の版違い H-ver・同じ参考曲の別模倣 H-ref・別の参考曲 H-diff）と比べた（数値は git 履歴と `pnpm audit:accomp`）。

- 低音・和音のリズム、強弱の曲線、楽器・ミックスは GG のほうが H-ver より似ている（0.9〜1.0）。分散の音高は GG 0.11 で別の曲並み。**似る原因は音高ではなく、セルのリズム・輪郭・音域・密度と固定した表**（関門はほぼ落とさない）。
- 音色の 1.00 は設定値の比較で、耳への効き方は未計測（P-1）。同じ種からは baseKey を変えても同じ計画が出る（S5 で直す）。
- 先行例（アレンジャーキーボード等）では曲ごとの幅はユーザーの和音表から来る。伴奏主体モードには和音表が無いので、構成と和声の幅もスタイルのデータに持たせる。

## 2. 全体構成

### 2.1 エンジンとスタイルの境界

| 置き場所 | 中身 |
|---|---|
| エンジン（いまは `src/compose/compose-accomp*.ts`。`src/accomp/` への引っ越しは S3） | 候補ループ・関門・保険の計画への退避／和声の理論／生成器（分散セル・低音型・和音の打ち方・色の線。後で持続音・オスティナート）／31平均律／強弱の正規化／MML 書き出し／監査／新しさの指紋／注釈から参照計画を組み立てる処理 |
| スタイル `src/compose/accomp-styles/<id>.ts` | 型・役割・句の表・パターンの表・層・固有の制約・閉じ方・切除対照・出所・監査の基準 |
| 参照 `references/<id>/` | 承認した手書き試作の MML と注釈。git で追跡する |
| 検査 `scripts/` | エンジンの検査・スタイルの検査（全スタイル）・監査 |

線引きの規則:

- **エンジンに、どのスタイルパックに出てくる id も書かない**（スタイル・役割・行・パターン id）。役割は閉じた語彙のタグ `RoleTag` だけで参照し、タグの語彙が増えていないことも検査する。
- スタイルに無い機能は汎用の生成器・制約として足し、2つ以上のスタイルで使うか「1スタイル専用」と明記する。
- 制約は2種類: **衛生**（エンジンが全スタイルに掛ける。和声・ぶつかり・表現・正規化）と**固有**（スタイルが宣言する。fb なら規則①〜⑤とループの閉じ方5点）。

- 入口は `composeAccomp({ style, baseKey, random, pick, recent })`。`style` を省くと `fb`。
- `references/` のファイル名・コメント、スタイルの id・`label`・`description` に参考曲名を書かない（公開 repo と unj-reze の IP の方針）。対応は gitignore のメモに置く。

### 2.3 compose.ts との関係

- `composeSong` は変えない。共有するのは下の層だけ: `resolveComposeKey`・`COMPOSE_SCALES`・`parseChord`/`spelledToUnits`・`DRUM_PATTERNS`・`GM_INSTRUMENT_RANGE`・`SOUNDFONT_BANKS`・`masterFxToMeta`。
- 使わないもの: `ComposeStats.score`（r = −0.06）、`SectionSpec`（J-POP の区間の意味を持つ）、歌メロ（層として呼べない）。
- 歌メロが主役の模倣先と、まばらな動機が乗る系統は当面対象外（後者は要るなら `motifCells` を S6 以降に）。

### 2.4 DAW との結合

S1 で直した（付録 F.8）。守ること:

- DAW は `ACCOMP_MIX` を import しない。作った曲の `song.mix` を当てる。
- `releaseAccompMix` は作った時点の `song.mix`（`composedAccompMix`）と比べ、MML 読み込みで捨てる。判定は純関数 `accompMixToRelease`。これを崩すと伴奏のディレイとループが後の歌ものへ漏れる。
- 上級者モードの枠は `LayerDef.presetSlot` から作る（`accompPresetSlots`）。直近の計画（将来は指紋）はスタイル id ごとに持つ。
- 「スタイルを足しても DAW と UI のコードは変わらない」を `check-accomp-styles.ts` が確かめる。
- 未: スタイルのプルダウン（登録表が2つ以上になったら）、ボタンの説明文を登録表から出すこと。

### 2.5 `#compose` の書式

- `style:<id>.v<version>:<baseKey>:<k>`（例 `style:fb.v1:major:3`）。計画を丸ごと与えたときは `…:plan`。`formatAccompCompose`・`parseAccompCompose`（`compose-accomp.ts`）。
- スタイル id は `/^[a-z0-9_-]+$/`（`.` と `:` は区切り。`@` は `mml-parser.ts` の値の文字集合で切れる）。
- 旧書式 `accomp:<baseKey>:<k>` も読み、`fb` 版1・`legacy: true` として扱う（1・2日目の試聴ファイルのため）。
- 版は、同じ文字列から同じ曲が出なくなる変更のたびに上げる。古い版は再生成できるように残さない（投稿は MML 本文を持つので、`#compose` は出所の記録）。

## 3. スタイルの型

### 3.1 型（要点。正は `src/compose/accomp-styles/schema.ts`）

- `StylePack`: `id`・`version`・`label`・`description`・`provenance`（承認した手書き試作だけ。採譜は使わない）・`key`（`modes`・`minorPolicy`）・`meter`（いまは 4/4・16分格子だけ）・`layers`・`roles`・`archetypes`（重み付き）・`harmony`（句の表・借用の組）・`patterns`（arp/bass/comp）・`compRules`（和音の打ち方の優先順位）・`constraints`（固有の制約。各々 `ifRoleMissing: "skip" | "fail"` 必須）・`seam`（閉じ方）・`ablations`・`variety`（`fixed`／`debt`／`baseline`）。
- `Row<T>`: `id`・`body`・`weight`・`energy`（0 抜け〜3 山）・`mask`（和音の種類・長さ・4小節内の位置・境目）・`from`（出所。変形で作った行は `approved: true` まで引かない）・`fits`（合う型。省くと起こした試作の型だけ）。
- `LayerDef`: `generator`・`presetSlot`・`window`（`relTo: "absolute"` は S5 まで。S5 で主音からの差にする）・`nonChordTones`・`params`。
- `Archetype`: `from`・`reference`（参照計画）・`tempo`・`seconds`・`form`・`arc`（強弱と山谷）・`mix`・`texture`・`groove?`（未実装）。
- `Mix`: `id`・`from`（承認したミックスだけ）・層ごとの GM 名・音源バンク・ストリップ・`master`。
- **`PlanPins`（計画の記録）**: 実現の段で決めるものはすべて計画に記録し、記録があれば実現の段はそれに従う。いまは `AccompPlan` の `style`・`archetype`・`mix` と、`AccompRegion` の `compHits`（小節ごとの打ち方 id）。記録が無いと、打ち方を表から引くようにした時点（S4b）で参照計画が fb を再現しなくなる。
  - 記録に無いもの: 和音の置き方・分散の組の同点を割る乱数、色の線の度数の順。だから `overrides.plan` で同じ曲になるのは候補 0 の曲だけ。

### 3.2 fb（最初のスタイル）

- `src/compose/accomp-styles/fb.ts`、版1。型は1つ（fb そのもの）、ミックス1つ、7役割（home・minorDwell・borrowA・glimpse・borrowB・lift・return）、4層（color・arp・bass・comp）。
- 固有の制約: r1 rateBand・r2 contrast（写しの組 glimpse/return と home）・r3 forbiddenMotion・r4 dynamicsOrder（山谷は型が宣言）・r5 borrowSubset。閉じ方は `loop:halfCadence`（最終小節 `Vsus4 V`）。
- S1 のエンジンがまだ読まない欄（宣言だけ）: `compRules`（S3a）・制約の判定（S3d）・`seam`（S3e）・`RoleDef.harmony`/`derive`（S3f/S3c）・行の `energy`/`mask`/`fits`（S2）・`variety`。`ablations` は未記入（切除対照16項目は `check-compose-accomp.ts` のまま）。
- 役割 id は S3g まで閉じた型 `AccompRole` のまま（`StylePack<AccompRole>`）。型とミックスは引かない（引くと乱数列がずれて黄金値が変わる。引く乱数列は S4a で決める）。
- `engineSupportProblems` が、型1つ・7役割の並びと順・4層などのいまのエンジンの前提を読み込み時に確かめる。
- 規則④はいま plan と check の2か所にある。S3d で1つの制約にまとめる。

### 3.3 2つ目の模倣先の例: 短調の持続音ループ（`tmp/deq/yoru.v3.mml`。所有者の評価は未確認）

ハ短調・C の持続・70BPM・24小節、オスティナート＋持続ベース＋短い和音。これを書くとエンジンに足りないもの（約7機能。機能の種類ごとに1回足せばよい）が見える: `parseChord` 基準の和音の語彙（いまの `degreeOf` は sus2・b9・11・13 で例外、`5` を sus4 と誤読）、旋法を基準にした借用の判定（いまは常に平行長調へ寄せる）、持続音・オスティナートの生成器と N 層、層を抜く `"off"`、同じ役割の再出現、層ごとの非和声音。旋律は当面入れない。

## 4. スタイル内のばらつき

### 4.1 引く順番

L0 型 → L1 区間の長さ → L2 和声（句・借用の組・和声のリズム）→ L3 リズムと置き方（低音・和音のパターン、借用和音の打ち方、ボイシング、分散の窓と密度）→ L4 分散のセル → L5 音高（いまのまま）。

- **型は承認した手書き試作1本から1つ起こす。** 独立に引いた軸を組み合わせても、一緒に設計した組み合わせにはならない。型の中の軸は一緒に引き、L1〜L5 は独立に引く。
- 別の試作の行を型の中で混ぜると同じ問題が戻る。対策1: 行の `fits`。対策2: 所有者が聴いた（型, 行）の組を `references/<id>/heard.json` に記録し、監査で「聴いていない組が引かれた割合」を出す（3割超で警告。仮の値）。
- パターンの行はエネルギー段で持ち、型が役割ごとに段を指定する。借用和音の小節の打ち方も型ごとの表にする（S4b。fb の型は long のまま）。
- 既存の表の再配置だけでは耳に届く差は小さい。新しい行には新しい試作が要る。試作の和音は、いまの解析が通すものだけ（sus2・5・11・13・b9 は S5 まで使わない）。

### 4.2 テンポ・揺れ・拍子

テンポ帯は型に持たせ、秒数か長さも一緒に動かす（fb の76小節が150〜180秒に収まるのは約101〜121BPM。lint で全テンポを確かめる）。揺れ（swing）と 4/4 以外の拍子は、実現の段にコードとエンジンの検査が要る。

### 4.3 表の lint（読み込み時。S2 から）

- `fixed` に無い軸は選択肢3つ以上・1つの重み0.6以下。設計で固定する軸は `fixed`、一時的な不足は期限付き `debt`、どちらにも無ければ落とす。
- 「耳に届く違い」: リズムは発音位置の Jaccard 0.6未満、セルはさらに輪郭が2か所以上、窓は3半音以上、楽器は GM かバンク、句はローマ数字が2小節以上（前後の入れ替えだけは同じ）。
- 行ごとに `from` 必須。窓を `GM_INSTRUMENT_RANGE` と照合。参考曲名の lint はローカルだけ（一覧が無いので未作成）。

### 4.4 新しさ（S4c）

- いまの `recent` は `planSignature` の完全一致で、実際には働いていない。指紋: 型 id・ミックス id・借用の組・長さの区分・区間ごとの和音パターンの族・分散セルの族。直近5曲のどれかと型が同じで他が3つ以上同じなら候補を飛ばす。順位は付けないので `pick` の再現は変わらない。関門が優先、両方満たす候補が無ければ新しさを外す。
- 試聴の束には、同じ型から引いた組を必ず1つ入れる（不満は「同じスタイルの曲どうしが似る」なので）。

### 4.5 ばらつきの監査（`scripts/accomp/audit-accomp-variety.ts`、`pnpm audit:accomp`）

- MML だけを読むので全スタイルに同じコードで使える。**報告だけ**（`pnpm test` に入れない）。
- 語彙は発音位置の Jaccard で重み付けた重なり（貪欲な輸送）。形＝位置の Jaccard × 輪郭の一致。音色は音源バンク・EQ・パン・送りまで比べる。曲の頭（最初の16小節）と継ぎ目を別に測る。
- 基準: `references/fb/baseline.json` は承認した試作の組だけ（H-ver: fb~fa、fb~長い寄り道は `draft` 印。H-part: backing との組は表示だけ）。却下された試作や参考曲名が分かる組は gitignore の `tmp/audit/fb.baseline.local.json`（`--local-baseline`・`--no-local`）。報告はローカルの基準込みで読む。しきい値の横に n とブートストラップ95%区間を出す。
- しきい値: 段階A＝H-ver の平均以下、段階B＝H-ref と H-ver の中点。値は数え方を直した後に測った報告で読む。
- **ほぼ重複の規則**: 型の中の組は、型が固定しない4指標（1小節の和音の語彙・低音のリズム語彙・和音のリズム語彙・分散の形の語彙）のうち3つ以上が H-ver の平均以上ならほぼ重複。型の間の組は7指標で別に報告。いまは型1つで99%がほぼ重複。上限の割合は S2 の後に決める。
- 未作成: 写しの長さの上限（参照計画と全層同じ小節の連続は4小節まで）・曲の中の対比・音の指標（重心・tilt・RMS 変動）・ラベルとの一致（AUC）。
- **較正**: ラベル（同じ曲に聞こえる／別に聞こえる）が両クラス10組以上たまるまで報告だけ。ラベルは試聴日の「同じ型の組」への所有者の感想から集める（較正専用の目隠し試聴はしない、§9.1.1）。
- **監査の値で候補を選んだり行を自動調整したりしない。**

見込み（未検証）: 和音の型を役割ごとに3つにしても、借用和音の小節（約30%）が long 固定なら和音のリズムの一致は約0.77止まり（段階Aに届かない）。分散はセルの行と段ごとの窓・密度を足すまで動かない。

## 5. 品質の守り方

- **関門**: 衛生（エンジン）＋固有（スタイルの `constraints` と `seam`）。落ちたら次の候補。採点で選ばず、関門を通った最初の候補を採る。
- **陽性対照**: 型ごとに参照計画を1つ持つ（いまは `scripts/test/fixtures/accomp-fb-plan.ts` の手書き。将来は注釈から組み立てる）。参照計画は全調・型のテンポ帯の全テンポで関門を通ること。
- **往復の下限**（参照計画を鳴らした MML と参照 MML、区間を揃えた値）: fb はリズム 分散1.00／低音0.98／和音1.00、音高 0.24／0.83／0.82（実測を切り下げ）。型ごとにその型で測った値を下限にする。
- **切除対照**: 固有の制約を1つ外したら、その関門が改変した参照計画を捕まえること。スタイルのデータとして持つ（fb の16項目は S3 以降に `fixtures/styles/fb/ablations.ts` へ）。
- **退避の率を数える**: 保険の計画は引いた型の参照計画そのものなので、退避が増える＝似る。候補が落ちた数と、計画の中の引き直し（`LENGTH_TRIES`・`TEXTURE_TRIES`・`OFFSET_TRIES`）の使い切りを、`composeAccomp` の `diagnostics` と `planAccomp` の `diag` で数え、監査が集計する（出力は変えない）。いまは600曲で退避0・k=0 通過 600/600・使い切り0。行を足して k=0 の通過が50%を下回ったら足した行を疑う。
- **出所と試聴**: 行とミックスはすべて承認した手書き試作まで辿れること（採譜は統計にだけ使う）。スタイルの版を上げる前に所有者に聴いてもらう（`accomp-audition --style <id>`、1日3本まで）。

## 6. 新しい模倣を足す手順（見積もり）

参考曲を決める → 手書きの試作を2〜3本（1本だと表が役割ごとに1行に戻る）→ 所有者が承認 → `references/<id>/` に置いて注釈 → スタイルを書く（型は試作1本につき1つ）→ 型ごとの参照計画・往復の下限・切除対照 → 検査と監査 → 試聴（型ごとに1曲と同じ型の組）。

所要は fb 系統の中ならエージェント約1〜1.5日＋所有者の試聴3〜4日。系統の外（いま挙がっている参考曲の多く）はエンジンの機能追加が乗る。新しい種類の生成器・制約・和音・閉じ方・拍子・揺れはコードが要る。

### 9.1.1 既定値（2026-09-28、所有者が設計を承認。耳で決めるものは各段階の試聴で直す）

### 9.1.2 見つかった問題: 伴奏主体モードに音量の段取りが無い（2026-09-29）

- 伴奏主体モードは「おまかせマスタリング」を通らず、`fb.ts` のミックスの音量は 80 固定。安全リミッター（`src/audio/safety-limiter.ts`）の手前を測ると、fb（FluidR3・80）は46ms 窓のピーク中央値 1.22、閾値超えの窓が90%。**音符の v と区間の強弱の山がリミッターで潰れて鳴っていた。**
- 試聴用（P-1・P-3）の6本は、リミッターに当たらない #volume に下げて渡した（聴こえる音量は約6dB 小さくなる）。
- **直し方（S2 に入れる。未実装）**: ミックスごとに承認時に測った音量（`Mix.master.volume`）を持たせ、リミッター手前の上位1%のピークが 0.85 以下になる値にする。測れるのはブラウザだけなので、計測の道具を scripts へ上げてミックスの承認手順に入れる。版を上げる。

## 付録 F: 段階 S0・S1 で設計からずらした点

どちらも出力の音を1音も変えていない。S0 で変わったのは `#compose` の文字列だけ、S1 で変わったのは計画に足した記録の欄だけ（黄金値の計画の sha256 だけを取り直し、MML の列は1文字も違わない）。

- **F.1 置き場所**: `src/compose/compose-accomp*.ts` は名前も書き出す名前も変えない（同時に別の作業が読んでいたため）。`src/accomp/` への引っ越しは S3。型 `schema.ts` もスタイル側に置いた。`#compose` の関数は `compose-accomp.ts` にあり、`src/index.ts` からは出していない。
- **F.2 監査の基準**: 却下された試作の組はローカルの基準へ分けた（§4.5）。CI では H-ver が n=2 で H-ref・H-diff は出ない。最終小節はリズムは全組同じだが音高まで同じなのは約3割（窓が絶対 MIDI のため）。
- **F.3 `references/fb/`**: `fa.mml` はヘッダの参考曲名を消した。fa は所有者が fb と比べて選ばなかった版なので `baseline.json` では `status: "alternative"`（行 `ho_fa` の出所なので `provenance` には残す）。`heard.json` は1・2日目に聴いた曲の行。和声の句の行 id は計画に残らないので未記録。
- **F.4 黄金値**: 設計より多く、変種100曲を足した（DAW で選べる31平均律と、`pick`・`recent` の経路を番するため）。
- **F.7 S1 のスキーマに足した欄**: `Row.note`・`LayerDef.params`・`RoleDef.label`/`supportedLengths`・`Archetype.reference` の `lengths`/`harmonyPicks`/`texturePicks`（注釈ができるまでの参照計画の選び方）・`arc.offsetMax`/`accents`・`CompHitsBody.alternate`（打ち方 id から形を選ぶ規則）。行の `weight` は 1 の仮置き。変形で作った行は `approved` を付けたが、S1 では絞らない（S2 の lint から）。`compose-accomp-tables.ts` は互換の口で、エンジンは読まない（検査あり）。
- **F.8 計画の記録と DAW**: 計画器は `style`・`archetype`・`mix` を書き、実現の段が `compHits` を決めて返し、入口が曲の計画に埋める。記録が壊れていれば例外か関門「表現」で落とす。キープや読み込みの曲は覚えた `#compose` と一致しないので、そのスタイルの全ミックスのどれかと一致すれば戻す。候補 1 以降と保険の計画は `overrides.plan` に渡すと同点の割り方が変わりうる。
- **F.10 検証の回で直した点**: `engineSupportProblems` が並びの順を見ていなかった（陰性対照を足した）。MML 読み込みで `composedAccompMix` を捨てる1行を足した（S4a で型ごとにミックスが増えると漏れるため）。
- **直していない点**: fixture の minorDwell 36小節目（`Vsus4 V`）の打ち方の記録は `alt13`。手書き元の読みなら `short2` だが、2和音の小節では形が同じで音は同じ。打ち方ごとに2和音の形が違う行を足す S3a・S4b で決め直す。
