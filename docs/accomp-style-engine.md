## 0. 1ページで

- **結論**: `composeAccomp` を「スタイルのデータを読む解釈器（スタイルエンジン）」に作り替える。
  - fb はその最初のスタイル `fb` になる。
  - fb 系統の中の模倣先は、スタイルのデータを1つ足すだけで済むようにする。
  - 系統の外の模倣先（短調の持続音・旋法・別の拍子など）は、最初の数本でエンジンに汎用の機能を足す。2つ目の模倣先だけで約7機能・約2〜4日（§3.3、見積もり）。いま名前が挙がっている参考曲の多くは系統の外にある。
  - `composeSong`（歌メロが主役の J-POP）は触らない。3つ目のエンジンも作らない。
- **いま似る原因**: スタイル全体で1通りに固定されているもの。音高の選び方ではない。
  - 楽器とミックス（48曲すべて同一）。
  - 区間ごとの低音と和音のリズム（役割ごとに1つ。和音の約3割は、区間の選択より先に和音の種類で打ち方が決まる）。
  - 分散のセルのリズム・輪郭・音域・密度（音域窓は48曲で1通り）。分散は毎秒4〜5音で鳴る主役の層。
  - 強弱の曲線と区間の並び（並びは1通り、強弱は区間ごとの ±2 のずれだけ）。曲の頭（home 16小節）と最終小節も全曲同じ。
  - 表は fb 1曲から起こしたので、「1曲の編曲」を書いていて「スタイルの幅」を書いていない。生成曲どうしは、生成曲と fb のあいだと同じくらい似ている。
- **懸念1「似たものしか出ない」への答え**:
  - スタイルの中に**型（archetype）**を複数持たせる。型は、ミックス（音源バンク込み）・テンポ帯と長さ・強弱の曲線・区間の並びの変種・層ごとの密度を一緒に設計した束。1曲はまず型を1つ引き、その中身を引く。アレンジャーキーボードの Main A〜D にあたる。
  - 和音・低音のリズムと分散のセル・音域・密度を、役割ごとに1つから、**エネルギー段ごとの表**（1段に3つ以上）に変える。借用和音の小節の打ち方も表にできるようにする。
  - 1行しかない和声の句の表を3行以上にし、借用の組を本当に別の和音の組にする。
  - 行は必ず、所有者が**承認した**手書きの試作から起こす。承認済みの fb・fa・backing は、もう行になり切っている。だから表を広げる前に、新しい試作を2〜3本書いて承認をもらう（段階 P-3）。
  - ばらつきは**監査で測る**（MML だけを読む）。型の中の組は、型が固定しない指標だけで判定する。型の間の組は別に報告する。**測った値で曲を選ばない。**
- **懸念2「保守が面倒」への答え**:
  - エンジンにスタイル名・役割名・表の行 id を書かない。lint で0件を保つ（いまは役割名の文字列だけで64か所）。
  - 足りない機能は、汎用の生成器か汎用の制約として足し、エンジン側の検査を付ける。スタイルごとの分岐は書かない。
  - 検査はエンジン用1本（大きさ固定）と、スタイル用1本（全スタイルを同じコードで回す）。スタイルが増えると実行時間だけが増える。
  - 参照計画は、注釈した手書き MML から組み立てる。計画の型を変えても、スタイルごとに書き直さずに済む。
  - DAW と UI も、スタイルを足しても変わらないようにする（いまは `ACCOMP_MIX` と4枠を直接見ている）。
  - 新しい模倣1つの所要（fb 系統の中、見積もり）: エージェント約1〜1.5日。所有者の試聴は3〜4日に分けて1日3本まで、合計約30〜45分。系統の外なら、これにエンジンの機能追加が乗る。
- **移行**: 先に src を触らずに試験をして、何を変えれば似なくなるかを所有者の耳で確かめる。
  - P-1: 60秒の抜粋を、ミックスだけ3通りに変えて鳴らす。
  - P-2: 型を手で2つ書き、テンポを変えた1本も鳴らす。
  - P-3: 新しい手書き試作を2〜3本書いて、承認をもらう。
  - 較正のラベル集め: 聴かない段階の日に分けて行う。
  - その後の順番:
    1. 表を移す（出力は1バイトも変えない）。
    2. P-3 の試作から fb の表をデータで広げて、3日目の試聴。
    3. fb 固有のコードを解釈器へ移す（1バイトも変えない。小分けにする）。
    4. 型とミックス（S4a）→ 借用和音の打ち方（S4b）→ 新しさと較正（S4c）。それぞれ1日ずつ試聴する。
    5. 2つ目の模倣先を足す。
  - どの段階も、前書の「1日3本まで」（§11・§12.7）の中で組む。

## 1. いま似る理由

### 1.1 計測の方法

- 使ったのは `scratch/accomp-variety.ts`（gitignore）で、約4秒で終わる。
  - 生成48曲（baseKey major/minor/any × 16種）を `accompToMml` → `parseMML` で読み、組ごとの類似度（1＝同一）を出す。
  - 別の種（777、60曲）で測り直すと、ほとんどの指標で平均の差は0.06未満だった。例外が2つある。
    - 強弱の曲線の形（GG）: 0.714 → 0.629（差 0.085）。
    - 借用の組の一致（G-fbP）: 0.563 → 0.417（差 0.146）。
  - 強弱の指標は、種を変えるだけで §4.5 の段階Aと段階Bのしきい値の差（0.04）より大きく動く。
- 組は次の5種類。

| 記号 | 組 | 組の数 |
|---|---|---|
| GG | 生成曲どうし | 1128 |
| G-fb | 生成曲 vs 手書きの `fb.space.mml` | 48 |
| H-ref | 同じ参考曲を別々に手で模倣した組（くもり空 s1/s2/s3、海の底 umi/s4、活火山 kazan/s5、断層 dansou/s5） | 6 |
| H-diff | 別の参考曲を模倣した手書きどうし | 49 |
| H-ver | 同じ曲の版違い（fb/fa、fb/長い寄り道、deq の v1/v2 ×5） | 7 |

- 「語彙」は、1小節の型がそれぞれの曲に出る頻度の重なりで、位置は問わない。「形」は、小節内の発音位置と、小節内での相対的な高さ。
- 移調は組ごとに合わせた。音高クラスの分布が最も近くなる移調を使う。生成曲どうしでは、1128組すべてで rootShift の差と一致した。
- **基準の組は小さく、所有者の承認も無い**（詳しくは §4.5）。
  - H-ref の6組は、どれも所有者が却下した v4 の試作（s1〜s5）を含む。旋律の層を持ち、楽器が違い、長さは32〜36小節（生成曲は72〜84小節）。
  - H-ver の7組には fb~長い寄り道が入っている。長い寄り道は fb のレビュー前の下書きで、7指標中6つで H-ver の平均以上になり、平均を押し上げている。
  - 和音の H-ref は0組（下の注）。

読み方:

- 低音と和音のリズム、強弱の曲線は、生成曲どうしのほうが「同じ曲の版違い（H-ver）」より似ている。
- GG と G-fb がほぼ同じ値になる。どの生成曲も、他の生成曲と同じくらい fb に似ている。
- **分散: 音高の選び方は似る原因ではない。似る原因は、セルのリズム・輪郭・音域・密度のほう。**
  - 分散の音高（0.11）は、別の曲どうし（0.05）と大差ない。
    - fb を計画として鳴らした版も、分散の音高で fb と一致するのは 0.25 だけ。それでも所有者は1日目を「だいたい良い」とした。
  - 一方で、次の4つは版違いより似ている。
    - リズム語彙 0.69（H-ver 0.48、H-diff から H-ver までの距離を1としたとき 1.56）。
    - 形の語彙 0.55（H-ver 0.39、同じく 1.41）。
    - 音域 0.95（H-ver 0.67）。
    - 密度 0.98（H-ver 0.85）。
  - 計画を見ても、分散の音域窓は48曲で1通りしか出ない。
  - 分散は毎秒4.3〜4.7音で鳴る主役の層なので、ここが固定だと耳に届く。
- **音色は音符の指標に出ない。**
  - 楽器・ミックスの 1.00 は設定値を比べた値で、音を聴いて比べたものではない。
  - しかも比べているのは、プリセット・役割ごとの GM 名・マスタの残響とディレイだけ（`scratch/accomp-variety.ts:411-421` の `TIMBRE_FIELDS`）。音源バンク（`#tNfont`）・EQ・パン・送りは見ていない。バンクだけ、EQ だけを変えたミックスも 1.00 になる。
  - 48曲とも、同じ Lead 1 (square)・Synth Bass 1・Electric Piano 2 が、同じ EQ・同じ送りで鳴る。
  - これが耳にどれだけ効くかは計測できていない。§8 の試験 P-1 で確かめる。
- **曲の頭が全曲同じ。**
  - home は16小節に固定（`REGION_LENGTHS`、`compose-accomp-tables.ts:61`）。
  - home の低音は walk、和音は short2 に固定（`ROLE_TEXTURE`、`:707-710`）。
  - 最終小節は全曲同一（§1.3）。
  - 聴き手は曲の頭で「似ている」と判断するが、いまの指標は曲全体の平均しか見ていない。

### 1.3 計画の側から見た固定（棚卸し、6000回の抽選）

| 項目 | 実効的な選択肢の数 | 場所 |
|---|---|---|
| ミックス・楽器 | 1 | `compose-accomp-tables.ts:1136`（`ACCOMP_MIX`）、`compose-accomp.ts:309` |
| 旅程（7区間の並び） | 1 | `compose-accomp-tables.ts:28` |

| 和音の段（`compRegister`）とボイシング | 段は2（minorDwell だけ −1 か 0）。ボイシングの規則は1つ | 同上、`COMP_VOICING`（`:977`） |

加えて:

- **和音の打ち方は、区間の選択より先に和音の種類で決まる小節がある**（`compHitsFor`、`compose-accomp-realize.ts:384-410`）。
  - 200曲で数えた（`scratch/comp-forced.ts`）。最終の一打 final 2.6%、予告 fore 3.9%、借用和音で長く伸ばす long 23.5%。計30.0%。
  - **borrowA と borrowB は、全小節が long。** fb の計画でも76小節中16小節が long。
  - 役割ごとに選べるのは残りの70%で、選べる型は short2 と alt13 の2つしかない。
  - この打ち方は実現の段で決まり、計画（`AccompPlan`）には載らない。区間ごとに持つのは `texture.comp` の1つだけ。
- 全小節の11.2%は、home の音符をそのまま写した小節（return の頭と最終小節）。最終小節はすべての曲で同じ。
- **同じ種からは、baseKey（major/minor/any）を変えても同じ計画が出る**（20種中20）。
  - 調は別の乱数列から引き（`compose-accomp.ts:359-361`）、候補は呼び出し側の乱数列から引く（`:398`）ため。
- ばらつきの検査は `planSignature` の種類数だけ（`check-compose-accomp.ts:830`・`:1697`）。
  - ID の違いを数えるので、耳に届かない違い（±2 の v のずれなど）でも別物と数える。40曲で40種となり、検査は通ってしまう。
- 関門で落ちる候補はほとんど無い。候補 k=0 が通った曲は57曲中57曲。似る原因は関門ではなく、固定した表にある。

### 1.4 まとめ

- 似る原因は、スタイルとして固定した量が多いこと。音高の抽選を増やしても効かない。
- モーツァルトのさいころ遊びと同じ形をしている。1小節に11通りあっても、和声と終止の役割は小節ごとに決まっている。組み合わせの数は多いが、聴いて違うものは少ない。
- 先行例（アレンジャーキーボード、Band-in-a-Box、Impro-Visor）でも、スタイルそのものは意図して同じに鳴る。曲ごとの幅は、ユーザーが渡す和音表と構成から来る。伴奏主体モードにはユーザーの和音表が無いので、構成と和声の幅もスタイルのデータに持たせる必要がある。

## 2. 全体構成

### 2.1 エンジンとスタイルの境界

| 置き場所 | 中身 | いまの場所 |
|---|---|---|
| エンジン `src/accomp/` | 候補ループ・関門の実行・保険の計画への退避／和声の理論（旋法を基準にする）／生成器（分散セル・低音型・和音の打ち方・色の線。後で持続音・オスティナート）／31平均律の綴り／強弱の正規化／MML の書き出し／監査／新しさの指紋／注釈から計画を組み立てる処理 | `compose-accomp*.ts` の汎用部分（約58%。下の注） |
| スタイル `src/compose/accomp-styles/<id>.ts` | 型・役割の定義・句の表・パターンの表・層・制約の設定・閉じ方・切除対照・出所・監査の基準 | `compose-accomp-tables.ts`（1,161行／4,959行＝約23%）と、fb 固有のコード（約19%。棚卸しの H1〜H26）をデータにしたもの |
| 参照 `references/<id>/` | 承認した手書き試作の MML と注釈（区間の区切り・小節ごとの和音・4小節ごとの行 id）。型ごとの参照計画はこの注釈から組み立てる。git で追跡する | いまは `tmp/`。gitignore なので CI には無い（`scripts/test/fixtures/accomp-fb-plan.ts:13`） |
| 検査 `scripts/` | エンジンの検査1本・スタイルの検査1本（全スタイルを回す）・監査 | `check-compose-accomp.ts`（159項目） |

注: 表の23%は行数で数えた。fb 固有の約19%は棚卸しの見積もりで、汎用の約58%はその残り。汎用と fb 固有の境目は、行単位では数え直していない。

線引きの規則:

- **エンジンに、どのスタイルパックに出てくる id も書かない。** スタイル id・役割 id・表の行 id・パターン id のすべてが対象。
  - 役割は、閉じた語彙のタグ（§3.1 の `RoleTag`）だけで参照する。
  - lint は、全スタイルパックに出てくる id の文字列を集め、エンジンのコードでの出現を数えて0件を保つ。いまの数は次のとおり。
    - 引用符つきの役割名: entry 7・plan 34・realize 6・check 17 の計64か所（tables の7か所は除く）。
    - `.home` のようなプロパティ参照: plan 16・check 1。
    - 行 id とパターン id: realize の `basic("final")`・`"fore"`・`"short2"`・`COMP_HITS.long`・`COMP_HITS.alt13`（`compose-accomp-realize.ts:394-409`）。plan の `FB_HARMONY_SCRIPT` と `FB_TEXTURE_SCRIPT`（`compose-accomp-plan.ts:882-907`。`"ho_fb"` のような行 id と、`"borrowA.first"` のようなキー）。
  - タグの語彙が増えていないことも検査する。タグがスタイル id の言い換えになるのを防ぐため。
- スタイルに無い機能が要るときは、汎用の生成器か汎用の制約として足し、エンジンの検査を付ける。その機能は2つ以上のスタイルで使うか、「1スタイル専用」と明記する。
- 制約は2種類に分ける。
  - **衛生（hygiene）**: エンジンが全スタイルに掛ける。和声（非和声音の扱い）・ぶつかり・表現・正規化。
  - **固有（identity）**: スタイルが宣言する。fb なら規則①〜⑤とループの閉じ方5点。切除対照もスタイルごとに持つ。

### 2.3 compose.ts との関係

- `composeSong` は1行も変えない。`#seed` の再現と、その選抜ループもそのまま残す。
- スタイルごとに3つ目のエンジンを作ることはしない。エンジン1つあたり、src 約4,960行と検査約2,980行が要る。
- 共有するのは下の層だけ。

| 部品 | 場所 | 使い方 |
|---|---|---|
| 調の解決 | `resolveComposeKey`（`compose-keys.ts:346`） | そのまま。短調の扱い（平行長調へ寄せる／短調のまま）はスタイルが選ぶ |
| 音階・旋法 | `COMPOSE_SCALES`・`TONIC_CENTERS`（`compose-scales.ts:514,685`） | 旋法を基準にした「借用」の判定 |
| 和音の解析・綴り | `parseChord`・`spelledToUnits`（`chords.ts:57,100`） | sus2・5・11・13・b9・ø・dim を扱う |
| ドラム | `DRUM_PATTERNS`（`drum-config.ts:124`） | スタイルはパターン id を名指すだけ。生成器は書かない |
| 楽器の音域 | `GM_INSTRUMENT_RANGE`・`fitInstrumentOctave`（`instrument-presets.ts:260,375`） | 層の音域窓の lint |
| 音源バンク | `SOUNDFONT_BANKS`（`soundfont-banks.ts:30`） | ミックスの `font` |
| マスタ FX | `masterFxToMeta`（`master-fx.ts:71`） | 前書 付録 D にある複製をやめ、これを使う |
| 採点 | `ComposeStats.score`・`screen-*` | **使わない**（構造品質との相関 r = −0.06） |
| 区間のモデル | `SectionSpec`・`buildSectionPlan` | **使わない**（J-POP の区間の意味を持つ） |
| 歌メロ | `compose.ts:2751-5348` の中 | 層として呼べないので使わない |

- 歌メロが主役の模倣先（ゆなぎのテーマ曲など）は、このエンジンの対象外にする。`composeSong` か、手書き（handscore）で作る。
- 「雰囲気は伴奏が決める。旋律の重みは小さい」は、所有者が**くもり空系（fb 系統）について**下した判断。ほかの系統にも当てはまるとは限らない。
  - v4 の却下理由4つ（旋律・音色・空間・展開）の1つは旋律だった。
  - yoru.v3 は calliope の旋律を持ち、コインランドリーは歌の曲。
- 伴奏が主役で、まばらな動機が乗る系統は、`composeSong`（J-POP 専用）でもこのエンジンでも作れない。
  - 当面は対象外とする（§6 の境界）。
  - 要るなら、手書きの動機セルの表を置くだけの生成器 `motifCells` を S6 以降の候補にする（§9.1-4）。

### 2.4 DAW との結合（いまは検査が無い。このまま進めると気づかずに壊れる）

「スタイルを1つ足しても DAW と UI のコードは変わらない」を、検査の項目にする（§7）。

### 2.5 `#compose` の書式

- 新しい書式は `style:<id>.v<version>:<baseKey>:<k>`。例 `style:fb.v2:major:3`。計画を丸ごと与えたときは `…:plan`。
- スタイル id は `/^[a-z0-9_-]+$/` に限る。`.` と `:` は区切りに使うので、id に入ると読み分けられない。`validateStylePack` で検査する。
- `@` は使えない。`mml-parser.ts:205` の値の文字集合が `[\w:.-]+` なので、`@` のところで値が切れる。
- いまの `accomp:<baseKey>:<k>` は未コミット・未 publish なので、投稿された MML には入っていない。**名前は今のうちに変える**（段階 S0）。
- 版（version）は、同じ文字列から同じ曲が出なくなる変更のたびに上げる。
- 投稿は MML の本文を持つ（unj-reze `docker/init.sql:168` の注記）。`#compose` は出所の記録であって、再生には要らない。古い版を再生成できるように残すかどうかは、所有者の判断（§9）。

## 3. スタイルの型

### 3.1 型（抜粋）

```ts
type W<T> = readonly (readonly [T, number])[];   // 重み付きの表

/** スタイル id。/^[a-z0-9_-]+$/（`.` と `:` は #compose の区切り）。validateStylePack で検査する。 */
type StyleId = string;

/** 役割のタグ。閉じた語彙で、増えていないことを検査する。スタイル id の言い換えにしない。 */
type RoleTag = "home" | "peak" | "weakest" | "echo" | "borrow" | "loopStart";

/** 行やミックスの出所。所有者が承認した手書きの試作まで辿れること。聴いただけでは足りない。 */
type Provenance =
  | { ref: string; bars: [number, number] }          // 例 { ref: "fb", bars: [1, 4] }
  | { op: string; parent: string; approved: boolean }; // 変形で作った行。approved まで引かない

type StylePack = {
  id: StyleId; version: number;
  label: string; description: string;              // DAW の選択肢と説明文。参考曲名・作者名を入れない
  provenance: string[];                            // references/<id>/ の承認した手書き試作だけ。採譜は使わない
  key: { modes: W<"major" | "minor" | ScaleId>; minorPolicy: "parallelMajorHome" | "asIs" };
  meter: "4/4";                                    // いまは 4/4・16分の格子だけ。他の拍子はエンジンのコードが要る（§6）
  layers: LayerDef[];
  roles: Record<string, RoleDef>;                  // 役割 id はスタイルの中だけで使う文字列
  archetypes: W<Archetype>;
  harmony: { pools: Record<string, Row<PhraseRow>[]>; borrowSets?: Row<BorrowSet>[] };
  patterns: { arp?: Row<ArpCell>[]; bass?: Row<BassPattern>[]; comp?: Row<CompHits>[]; ostinato?: Row<ArpCell>[] };
  compRules: CompRule[];                           // 和音の打ち方の優先順位（いまの compHitsFor）
  constraints: Constraint[];                       // 固有の制約。衛生の制約はエンジンが持つ
  seam: SeamRecipe;                                // loop:halfCadence | loop:modal | stop:tonic | fade
  ablations: { mutate: string; expect: string }[]; // 切除対照（expect は制約 id）
  variety: {
    fixed: AuditAxis[];                            // 設計で固定する軸。合否から外し、値は表示する
    debt: { axis: AuditAxis; until: number }[];    // 一時的な不足。until の版を過ぎたら落とす
    baseline: string;                              // references/<id>/baseline.json（承認した試作の組と所有者のラベル）
  };
};

type Row<T> = {
  id: string; body: T; weight: number;
  energy: 0 | 1 | 2 | 3;                           // 0 抜け 〜 3 山
  mask?: Mask; from: Provenance;
  fits?: string[];                                 // 合う型の id。省くと、起こした試作の型だけに合う
};
type Mask = {
  chordClass?: ("maj" | "min" | "sus" | "dom" | "borrowed")[];
  span?: (0.5 | 1 | 2)[];                          // 和音の長さ（小節）
  barInBlock?: number[];                           // 4小節の中の位置
  boundary?: "pre" | "on" | "last";                // 区間の境目
};

type LayerDef = {
  id: string;
  generator: "arpCells" | "bassPattern" | "compHits" | "colorLine" | "pedal" | "ostinato";
  presetSlot: PresetSlot;                          // DAW の枠
  window: { lo: number; hi: number; relTo: "tonic" | "absolute" };  // absolute は S5 まで（いまの値のまま）
  nonChordTones: ("passing" | "neighbour" | "approach")[];
};

type RoleDef = {
  tags: RoleTag[];
  lengths: W<number>;
  harmony: Slot[];     // {pool, count?, noRepeat?, fill?, endsOn?} | {copy: {from, bars}} | {ref: "borrow.fore"}
  derive?: { from: string; transform: "same" | "liftVariant"; blockMap?: number[] };
  rate?: Partial<Record<string /* layer */, [number, number]>>;  // 規則①の帯（毎秒の音数）
};

/** 型: 一緒に設計した束。1曲はまず型を1つ引く。型は承認した手書きの試作1本から1つ起こす。 */
type Archetype = {
  id: string; from: Provenance[];
  reference: { annotations: string; mml: string }; // 型ごとの参照計画（注釈から組み立てる）と往復の下限の元
  tempo: W<number>; seconds: { min: number; max: number };  // lint: 参照計画が帯の全テンポで秒数に入る
  form: W<string[]>;                               // 役割の並び。S4 までは長さの違いだけ。役割を抜く・繰り返すのは S5 から
  lengths?: Partial<Record<string /* role */, W<number>>>;
  arc: { levels: Record<string /* role */, LevelSpec>; order: DynamicsOrder };  // 分散・低音・和音の強弱と、山と谷
  mix: W<Mix>;
  texture: Record<string /* role */,
    Record<string /* layer */, "off" | { energy: number[]; windowShift?: number; density?: [number, number] }>>;
  groove?: { swing16?: number };                   // いまのエンジンに無い。足すなら実現の段とエンジンの検査（§6）
};

type Mix = {
  id: string; from: Provenance;                    // 所有者が承認したミックスだけ（P-1 など）
  layers: Record<string, { gm: string; font?: string; strip: StripFx }>;  // EQ・パン・幅・送り
  master: { inst: string; volume: number; fx: MasterFx; drum: string | "none"; loop: boolean };
};

type CompRule = {
  when: { songLast?: true; lastOfTag?: RoleTag; foreshadow?: true; chordClass?: "borrowed" };
  hits: string | { energy: number[] };             // 決まった型か、エネルギー段の表から引くか
};

type Constraint = {
  id: string; kind: string;
  ifRoleMissing: "skip" | "fail";                  // 名指しした役割が並びに無いとき。省略不可
  /* kind ごとの引数 */
};

/** 計画に足す欄。実現の段で引くものは、すべてここに記録する。与えられたら、実現の段はそれに従う。 */
type PlanPins = {
  style: StyleId; archetype: string;               // 強弱（arc.levels）の出どころもこれで決まる
  mix: string;                                     // Mix.id
  regions: { compHits?: string[] /* 小節ごとの打ち方 id */ }[];
};
```

いまの型からの主な変更:

- `AccompRole`（`compose-accomp.ts:44-51`）の閉じた型をやめ、役割 id を文字列にする。
- `AccompMix`（`:166-188`）のリテラル型（`instrument: "retro_game"`・`drum: "none"` など）をやめる。
  - 音源バンクの欄を足す。いまの `AccompMix` には無く、`accompMeta`（`:456-485`）も `#tNfont` を書かない。
- `AccompSlot` の4値（`:154`）をやめ、層の数をスタイルが決めるようにする。
- 和音の打ち方の優先順位（`compHitsFor`）を、`compRules` というデータにする。
- **実現の段で決めているものを、計画に記録できるようにする（`PlanPins`）。** いま計画の外で決まっているものは2つある。
  - 借用和音の小節の打ち方: 和音の種類から決まる（`compose-accomp-realize.ts:384-410`）。
  - 低音と和音の強弱: 役割名から決まる（`LEVELS[region.role]`、`:741`）。
  - 記録が無いと、`compRules` を表から引くようにした時点で、fb の参照計画が fb を再現しなくなる（§5）。
- 音域窓は、S1〜S4 は `relTo: "absolute"` のまま（いまの値、`HOME_WINDOW` など `compose-accomp-tables.ts:639`。ホ長調で測った絶対 MIDI）。S5 で主音からの差に直す。ホ長調（rootShift 4）の出力は変わらない。

  - lint で、型の並びの変種と制約の組み合わせを全部確かめる。区間の並びの変種で役割を抜けるのは S5 からなので、それまでは起きない。

### 3.3 別の模倣先の例: 短調の持続音ループ（手書き試作 `tmp/deq/yoru.v3.mml` から）

yoru.v3 のヘッダの注記から読んだ事実:

- ハ短調で、ベースが C を持続する。70BPM・24小節（約82秒）。`#inst=ambient_cloud`・`#loop=on`。テンポは fb の帯（110〜116）の外にある。
- 層は4つ。
  - Music Box の8分オスティナート（3+3+2）。

  - 21〜22小節は、旋律とオスティナートが抜けて、和音とベースだけになる。

## 4. スタイル内のばらつき

### 4.1 引く順番

| 段 | 引くもの | いま | 目標（スタイルごと） |
|---|---|---|---|
| L0 型 | ミックス（音源バンク込み）・テンポ帯と長さ・強弱の曲線と山谷・区間の並びの変種・層ごとのエネルギー段 | 1 | 3以上（fb は段階 S4a で） |
| L1 区間 | 長さ（テンポと連動させる、§4.2） | 実効約25 | 維持 |
| L2 和声 | 句の表・借用の組・**和声のリズム**（1小節1和音／半小節2和音／2小節1和音。いまは句の行に埋まっている） | 1行の表が3つ。借用の組は実質1 | 各表3行以上。借用の組は、和音が本当に違うものを2つ以上。和声のリズムを行の段として持つ |
| L3 リズムと置き方 | 和音・低音のパターン（エネルギー段と条件で引く）、借用和音の小節の打ち方、**和音のボイシング（広さ・転回）と段**、**分散の音域窓と密度** | 役割ごとに1。借用和音は long 固定。ボイシングの規則は1つ（`COMP_VOICING`）、和音の段は2通り、分散の窓は1通り | 1段あたり3以上 |
| L4 分散のセル | セルのリズムと輪郭 | リズム語彙 0.69・形の語彙 0.55（H-ver 0.48・0.39 より似ている） | セルの行を試作から足す（1段あたり3以上） |
| L5 音高 | セルの中の音の選び方 | 分散の音高 0.11（別の曲並み） | 維持 |

主な軸は、上から効く順に次の6つ。

1. **型**（ミックス・テンポ帯・強弱の曲線・並びの変種を束ねたもの）
2. **和音と低音のリズム**（エネルギー段ごとの表。借用和音の小節も含む）
3. **分散のセル・音域・密度**（エネルギー段ごとの表）
4. **和声の句と借用の組**（1行の表をなくす）
5. **区間の長さと並びの変種**
6. **新しさの指紋**（引き直しで、同じ型・同じ組み合わせを続けない）

設計上の注意:

- **型は、承認した手書きの試作1本から1つ起こす。**
  - 独立に引いた軸を組み合わせても、fb のように一緒に設計した組み合わせにはならない（判定の指摘）。
  - 型の中の軸は一緒に引き、型の外（L1〜L5）は独立に引く。
- **別の試作の行を混ぜると、同じ問題が戻る。**
  - 型の中でエネルギー段の行を別の試作の行と入れ替えると、「独立に引いた軸」の組み合わせになる。
  - 関門はこれを区別しない（候補 k=0 が57曲中57曲で通る）。所有者も、型ごとに1曲くらいしか聴かない。
  - 対策1: 行に `fits`（合う型）を付け、`fits` に無い型では引かない。省いたら、起こした試作の型だけに合う。
  - 対策2: 所有者が聴いた（型, 行）の組を `references/<id>/heard.json` に記録する。監査で「聴いていない組が引かれた割合」を出し、3割を超えたら警告する（3割は仮の値）。
- **エネルギー段**:
  - パターンの行は、どの区間から起こしたかではなく、エネルギー段（0 抜け〜3 山）で持つ。型は役割ごとに段を指定する。
  - たとえば pulse8 は山の段、dropout は谷の段に置く。役割の意味は保ったまま、同じ段の別の行と入れ替わる（`fits` の範囲で）。
  - 条件（`Mask`）で、和音の種類・和音の長さ・4小節の中の位置・区間の境目を限る。いまのコードの `alternate`・`split`・`last` の規則（`compose-accomp-tables.ts:655-663`）は、多くが条件で書ける。
  - 分散の音域窓と密度も、段ごとに持つ（型が `windowShift`・`density` で寄せる）。
- **借用和音の小節の打ち方**:
  - いまは borrowA・borrowB の全小節が long（§1.3）。役割ごとの表を広げても、山の区間は変わらない。
  - `compRules` の `borrowed` を `{ energy: [...] }` に変え、型ごとに手書きの別案を3つ以上持つ。
  - 「借用和音は長く伸ばす」を fb の正体とみなすなら、ここは変えない（§9 の未決事項）。
  - どちらにしても、実現した打ち方は計画に記録する（§3.1 の `PlanPins`）。
- **既存の表の再配置だけでは、耳に届く差は小さい。**
  - `BASS_LIST` は12型あり、役割に割り当てられているのは1つずつ。ただし home に合うのは walk・walkLite・thinned で、3つとも発音位置 0・6・8 を共有する同じ付点のノリ。
  - 和音は、役割で選べる型が short2 と alt13 の2つしかない。
  - 承認した試作（fb・fa・backing）は、もう行になっている。HOME_OPEN は ho_fb・ho_fa の2行、MINOR_OPEN・MINOR_CLIMB・RETURN_END は1行ずつ、fb の和音は1小節のリズムが3種類。
  - ほかの試作（v4 の s1〜s5、deq の v1〜v3）は所有者が却下した（「引き込まれない」）。行の出所にはできない。
  - だから新しい行には新しい試作が要る。表を広げる前に試作を書く（段階 P-3）。
- **試作に使える和音**: いまの `degreeOf`（`compose-accomp-plan.ts:282-307`）は sus2（音程2）・b9・11・13 で例外を投げ、`5` を sus4 と読む。P-3 と S4a の試作は、いまの解析が通す和音だけで書く。sus2・5 の和音は参考曲の系統の主な色だが、`parseChord` 基準の語彙（S5）が入るまでは行にできない。

### 4.2 テンポ・揺れ・拍子と長さ

- テンポは、いまは1つに聞こえる（110〜116、GG のテンポの類似度 0.98）。参考曲のテンポは60〜200と幅広い（参考曲のメモ）。
- テンポ帯は型に持たせる（`Archetype.tempo`）。テンポを動かすなら、秒数の範囲か長さも一緒に動かす。
  - fb の76小節が150〜180秒に収まるのは、101.3〜121.6BPM のときだけ（76 × 240 / bpm）。
- lint: 型ごとに、参照計画が、その型のテンポ帯のすべてのテンポで、その型の秒数の範囲に入ること。いまの fb 専用の検査（`check-compose-accomp.ts:2024-2037`）を、全スタイル・全型へ一般化する。
- **揺れ（swing・shuffle・人の揺れ）**: いまの実現の段には仕組みが無い（`src/compose-accomp*.ts` に swing の語は0件）。足すなら、型の `groove.swing16`（16分の裏をどれだけ遅らせるか）を生成器の引数にし、エンジンの検査を付ける。検査の例: 裏の遅れが指定の比になる、継ぎ目で崩れない、関門のぶつかり判定が遅れた位置で行われる。
- **拍子**: いまは 4/4・16分の格子だけ。セル・低音型・和音の打ち方が16分の位置で書かれているので、3/4 や 6/8 はエンジンのコードが要る（§6）。`fixed` に書いて済ませる軸ではない。

### 4.3 表の lint（スタイルを読み込むときの検査）

- `fixed` に書いていない軸は、選択肢3つ以上、1つの重み0.6以下。
- 「耳に届く違い」を次のように決める。どれも満たさない2行は、同じ行として数える。

| 行の種類 | 違うとみなす条件 |
|---|---|
| リズムのパターン | 発音位置の集合の Jaccard が0.6未満（同じノリの族は1つと数える） |
| 分散のセル | リズムの条件に加えて、輪郭（小節内の相対的な高さの並び）が2か所以上違う |
| 音域窓 | 3半音以上ずれる |
| 楽器 | GM プログラムか音源バンクが違う |
| 和声の句 | ローマ数字の並びが2小節以上違う。前後の入れ替えだけなら同じとみなす（P2 のような行を捕まえる） |

- 選択肢が3つに満たない軸の扱い:
  - 設計として固定する軸は `fixed` に書く（例: 和声が一巡するスタイルの和音の語彙）。合否から外し、値は表示する。
  - 一時的に足りない軸は `debt` に書き、期限（スタイルの版）を付ける。期限までは警告として毎回表示し、過ぎたら落とす。
  - どちらにも書かなければ落とす。
  - 新しい模倣先を、試作1本でまず出したいときに止めないため。
- 行ごとに `from`（出所）を必須にする。`op` 付き（変形で作った行）は、`approved: true` になるまで引かない。
- 層の音域窓を、楽器の音域（`GM_INSTRUMENT_RANGE`）と照らし合わせる。
- ミックスは、そのスタイルで所有者が**承認した**ものに限る（`Mix.from`）。聴いただけの試作の楽器や、別の模倣先の試作の楽器は持ち込まない。
- **名前**: スタイル id・`label`・`description`・行 id に、参考曲名・作者名を入れない。
  - DAW のスタイル一覧は unj-reze の中で公開される。unj-reze の IP の方針（AGENTS.md）は、市販の作品名をサイトに出さないことを求めている。
  - 参考曲とスタイルの対応は、gitignore のメモに置く。
  - lint はその名前の一覧を読んで照らし合わせる。一覧は gitignore なので、この lint はローカルでだけ効き、CI では効かない。
- スタイル id は `/^[a-z0-9_-]+$/`（§2.5）。

### 4.4 新しさ（引き直しで似たものを続けない）

- いまの `recent` は `planSignature` の完全一致で判定している（`compose-accomp.ts:393`・`:416`）。6000回引いて一度も一致しなかったので、実際には働いていない。
- **指紋**の項目: 型 id・ミックス id・借用の組・長さの区分（短・中・長）・区間ごとの和音のパターンの族・分散のセルの族。
- 直近5曲のどれかと型が同じで、かつ他の項目が3つ以上同じなら、その候補を飛ばす。
- これは通すか飛ばすかを決めるだけで、順位は付けない。候補 k の中身は (seed, k) だけで決まるので、`pick` の再現は変わらない。
- 関門は常に優先する。関門と新しさの両方を満たす候補が無ければ、保険の計画へ退避する前に新しさの条件を外す。
- **試聴の束**（`accomp-audition`）には、同じ型から引いた組を必ず1つ入れる。所有者の不満は「同じスタイルから出た曲どうしが似る」ことなので、型の間だけを聴いても確かめられない。残りは、型を (batchSeed, 番号) から重複なしで引く。
- DAW は、直近の指紋をスタイル id ごとに持つ（§2.4）。

### 4.5 ばらつきの検査（監査）

`scratch/accomp-variety.ts` を `scripts/accomp/audit-accomp-variety.ts` に上げる。MML だけを読むので、どのスタイルにも同じコードで使える。

先に直すこと:

- **リズムと形の語彙を完全一致で数えない。**
  - いまは1小節の発音位置を文字列にして数えている（`scratch/accomp-variety.ts:246` の `poss.join(",")`）。形も、位置と高さの順位を文字列にして完全一致で数えている（`:252-262` の `join(" ")`）。
  - このため walk {0,6,8,12,14}・walkLite {0,6,8,12}・thinned {0,6,8} が全く別物として数えられ、耳に届かない差で合格してしまう。
  - 発音位置の集合の Jaccard で重み付けた重なりに変える。形は、位置の Jaccard と輪郭の一致の積にする。
- **音色の欄を増やす。** `TIMBRE_FIELDS`（`:411-421`）に、役割ごとの音源バンク・EQ・パン・幅・残響とディレイの送りを足す。
- **曲の頭と継ぎ目を別に測る。**
  - 最初の16小節（112BPM で約34秒）だけで、和音・低音・和音・分散のリズム語彙を測る。
  - 継ぎ目の小節（最終小節と曲の頭）が曲どうしで同じかを数える。
  - home を型ごとに変えないと決めたら（§9.1-1）、`fixed` に `opening` と書き、合否から外す。
- **基準をスタイルごとに持つ。**
  - 手書きの基準の MML を `references/` に置く。いまは gitignore の `tmp/` を読んでいる（`:568-587`）。
  - スタイルごとに、承認した試作の組を2つ以上、所有者のラベル付きで `baseline.json` に持つ。全スタイル共通の定数にはしない。
  - しきい値の横に、基準の組の数 n と、ブートストラップの95%区間を出す。
  - fb~長い寄り道には印を付け、除いた値も出す。

ほかの検査:

- **写しの長さの上限（MaxOrder）**:
  - 参照計画と比べて、和音・セル・低音・和音の打ち方が全部同じ小節が続く長さは、4小節まで。
  - 曲の中の写し（return が home を写すなど）は数えない。
  - 閉じ方の小節は、`seam` が固有の制約になっているときだけ除く。
- **曲の中の対比**: 規則②で落ちた候補の数と、隣り合う区間で変わった軸の数の分布を報告する。fb の値を下回ったら警告する。表を広げて規則②の棄却が増えると、実際に引かれる表が狭くなるため。
- **聴いていない組**: 引かれた（型, 行）のうち、`heard.json` に無いものの割合（§4.1）。
- `fixed` に書いた軸は合否から外すが、値は必ず表示する。

**較正（しきい値は、耳で確かめるまで仮の値として扱う）**:

- 監査は、ラベルが両方のクラス（同じ曲に聞こえる／別の曲に聞こえる）で10組以上たまるまで、**報告だけ**にする。10組は前書 §11 の「評価ラベルが10本たまってから」と同じ数。
- 生成曲の組だけでは較正できない。いまは型が1つで、1128組中1126組が前版の規則でほぼ重複になる。ラベルがほぼ全部「同じ」になり、「別」の側の例が無い。
- 組は層に分けて作る。各層4〜5組、計24〜30組。

| 層 | 中身 |
|---|---|
| H-ver | 同じ曲の版違い（fb/fa、deq の v1/v2） |
| H-ref | 同じ参考曲の別々の手書き（s1/s2 など） |
| H-diff | 別の参考曲の手書き |
| P-1 | 同じ計画で、ミックスだけ違う |
| P-2 | 手書きの型どうし、手書きの型と fb |
| 生成曲 | 同じ型から引いた組 |

- 聴かせ方:
  - 曲まるごとか、決まった60秒の抜粋。抜粋は全組で同じ位置（曲の頭から60秒）にする。
  - 抜粋を使うときは、指標も同じ60秒で計算し直す。
  - 全体の形と強弱の曲線は、抜粋では聴き取れない。この2つは、試聴日に聴く曲まるごとの組（同じ型の組、§4.4）でだけ較正する。
- 報告: 指標ごとに、ラベルとの一致（AUC）を n と一緒に出す。
- 音の指標も足す: スペクトル重心・tilt・RMS の変動係数。参考曲の計測と同じ `studio.play`＋analyser の方法で測る。音色の違いは設定値では測れないため。
- **前書との食い違い**:
  - 前書 §12.7 は「目隠しの A/B や順位付けはしない」とする。handover は「8小節の目隠し A/B は細かい採否に使えない」とする（前書 §11）。
  - 較正は名前を隠した組に「同じ／別」を付けるので、形は目隠しの A/B に近い。
  - 違いは2つ。問いが採否や好みではなく「同じ曲に聞こえるか」であること。抜粋が60秒（112BPM で28小節）あること。
  - それでも前書の方針から外れるので、所有者に確かめる（§9.1-7）。断られたら、試聴日の曲まるごとの組だけでラベルを集める（遅いが、方針には沿う）。
- **1日の量**:
  - 前書の上限（1日3本、1本2分半〜3分）に収める。
  - 60秒の組（2分）を何本分と数えるかは、所有者に聞く（§9.1-7）。聞くまでは組1つを1本と数え、1日3組とする。
  - 24〜30組なら8〜10日かかる。聴かない段階（S0・S1・S3）の日に回す。
- **監査の値で候補を選んだり、行を自動で調整したりしない。** 内蔵採点（r = −0.06）と同じ罠になる。

### 4.6 見込み（見積もり。未検証）

- 役割ごとに和音の型が3つあり、互いの発音の重なりが約0.5なら、区間を揃えた和音の発音の一致は 0.94 から約 1/3 + 2/3 × 0.5 ≈ 0.67 に下がる（案Aの見積もり）。

- 借用和音の打ち方も表にしないと、和音のリズムは段階Aに届かない見込み。語彙の指標も同じ向きに動くと見ているが、未検証。
- S2 を既存の行の並べ替えだけにした場合（P-3 の試作が承認されなかった場合）も、上限はこの約0.77。
- 分散は、セルの行とエネルギー段ごとの窓・密度を足すまで、リズム語彙 0.69・形の語彙 0.55・音域 0.95・密度 0.98 のまま動かない見込み。

## 5. 品質の守り方

- **関門**（落ちたら次の候補を引く）:
  - 衛生: 和声・ぶつかり・表現・正規化。エンジンが全スタイルに掛ける。
  - 固有: スタイルの `constraints` と `seam`。fb なら規則①〜⑤とループの閉じ方5点。
- **陽性対照**:
  - fb の32項目はそのまま残す（`romanToC` と fb 2・fbPlan 8・fb の実現 15・fb のミックス 3・ほか）。変わるのは import 先だけ。
  - **型ごとに**参照計画を1つ持つ。参照計画は、表を見ずに、注釈した手書きの MML から組み立てる（`FB_PLAN` と同じ考え方、`scripts/test/fixtures/accomp-fb-plan.ts:4-7`）。組み立ては注釈を読むエンジンの1か所で行う（§7.2）。
  - **実現の段で引くものは、すべて計画に記録し、参照計画はそれを固定する**（§3.1 の `PlanPins`）: 型 id・ミックス id・小節ごとの和音の打ち方 id。強弱は型の `arc` から来るので、型 id を固定すれば出どころも決まる。
    - いまは、借用和音の打ち方（`compose-accomp-realize.ts:384-410`）と、低音・和音の強弱（`LEVELS[region.role]`、`:741`）が計画の外で決まる。
    - `compRules` の borrowed を表から引く型を作った時点（S4b）で、記録が無ければ fb の参照計画は fb を再現しなくなる。fb の計画では、76小節中16小節が借用和音の long（`scratch/comp-forced.ts`）。
  - **往復の下限**（参照計画を鳴らした MML と、参照の MML を比べる。区間を揃えた値。層ごと）:

| 層 | リズム（fb の実測） | 音高＝同じ位置の発音＋音高クラス（fb の実測） |
|---|---|---|
| 分散 | 1.000 | 0.247 |
| 低音 | 0.986 | 0.831 |
| 和音 | 1.000 | 0.827 |

  - 下限は実測を小数2桁で切り下げた値にする（リズム 1.00／0.98／1.00、音高 0.24／0.83／0.82）。前版の「リズム 1.00」は、低音（0.986）では成り立っていなかった。
  - 型ごとに、その型の参照計画で測った値を下限にする。
  - 参照計画は、全調と、その型のテンポ帯の全テンポで、関門を通ること（いまの `fbPlan` と同じ）。
- **切除対照**: 固有の制約を1つ外したら、その制約の関門が、参照計画を改変したものを捕まえること。スタイルのデータとして持つ。fb の16項目は `fixtures/styles/fb/ablations.ts` へ移す。
- **採点で選ばない。** 関門を通った最初の候補を採る。監査の値と指紋は、選抜に使わない。
- **退避の率を数える**:
  - 保険の計画は参照計画そのもの（`compose-accomp.ts:431-432`）。型ごとに持つので、退避先は引いた型の参照計画になる。退避が増えると参照の複製が増える、つまり似る。
  - 候補が関門で落ちた数だけでなく、計画の中の引き直しを使い切った数も数える。対象は `LENGTH_TRIES`・`TEXTURE_TRIES`・`OFFSET_TRIES`（`compose-accomp-plan.ts:441`・`:845-872`）。使い切ると、検証していない下書きを返すため。
  - いまの値: 200曲中退避0。候補 k=0 が通った率は57/57。行を足してこれが50%を下回ったら、足した行を疑う。
- **行とミックスの出所**: すべての行とミックスが、所有者が承認した手書きの試作まで辿れること（`from`）。採譜（市販曲の書き起こし）は統計にだけ使い、行にはしない。
- **所有者の試聴**: スタイルの版を上げる前に聴いてもらう（`accomp-audition --style <id>`）。1日3本まで。束には同じ型の組を1つ入れる（§4.4）。

合計:

- fb 系統の中なら、エージェント約1〜1.5日と、所有者の試聴3〜4日（1日3本まで、合計約30〜45分）。
- 系統の外なら、これにエンジンの機能追加が乗る。2つ目の模倣先（§3.3）は約7機能・約2〜4日（見積もり）。
- いま名前が挙がっている参考曲の多く（Dequivsia・コインランドリー・0次元）は、fb 系統の外にある。最初の数本は機能追加込みで見積もる。「データを足すだけ」は、エンジンがその系統を覆ってからの話。

**コードが要らない範囲**:

- 既存の生成器で書ける模倣先。生成器は、分散セル・低音型・和音の打ち方・色の線。段階 S5 以降は、持続音とオスティナートも加わる。

**コードが要る境界**:

- 新しい種類の生成器・制約・和音・閉じ方が要るとき。その場合も、スタイルの分岐としてではなく、汎用の機能としてエンジンの検査付きで足す。

- 旋律が主役の模倣先（ゆなぎのテーマ曲など）は、このエンジンに入れない。
- 伴奏が主役で、まばらな動機が乗る模倣先も、当面は対象外。`motifCells` の生成器を足すまで（§2.3・§9.1-4）。

**スタイルごとに最低限そろえるもの**:

| もの | 置き場所 | 目安の大きさ |
|---|---|---|
| 承認した手書きの試作と注釈 | `references/<id>/` | MML 2〜3本 |
| スタイル本体 | `src/compose/accomp-styles/<id>.ts` | fb で表の約950行。小さなスタイルなら数百行 |
| 参照計画 | 注釈から組み立てる（型ごとに1つ） | 注釈は型ごとに数十行の見込み（未計測） |
| 切除対照 | `scripts/test/fixtures/styles/<id>/ablations.ts` | 固有の制約1つにつき1項目以上 |
| 黄金値 | 同じ場所の `golden.json` | 型ごとの参照計画と、5種×3調の MML ハッシュ |
| 監査の基準 | `references/<id>/baseline.json` | 承認した試作の組2つ以上と、所有者のラベル |
| 聴いた組の記録 | `references/<id>/heard.json` | 試聴のたびに追記 |

- 補助（任意）として、注釈した参照 MML から**行**の下書きを作る抽出スクリプトを作れる（案Bの `style-extract`）。
  - 下書きは手で確かめてから入れる。検査の中では使わない。
  - 段階 S6 以降に、手順5の時間が重いと分かったら作る。
  - 参照**計画**の組み立て（手順6）は、これとは別。注釈に行 id を書いておけば、逆変換は要らない。

### 7.2 何かを変えたときに壊れるもの

- **生成器を直したとき**:
  - それを使う全スタイルの黄金値が変わる。
  - 意図した変更なら、1コマンドで黄金値を取り直し（`pnpm accomp:bless`）、スタイルの版を上げる。
  - 黄金値は参照計画と少数の種だけにしておく。取り直しの件数はスタイル数に比例するが、1件あたりの手間は小さい。
- **スタイルを足したり直したりしたとき**: 他のスタイルには影響しない。`shared/` を触ったときだけ、それを使う全スタイルを回す。
- **計画の型（`AccompPlan`）を変えたとき**: 全スタイルの参照計画に効く。スタイル同士が独立なのは表の中身だけで、計画の型は共有している。
  - 予定している変更: S1 の役割 id の文字列化、S2〜S4 の `PlanPins`、S5 の主音からの窓と N 層。
  - 参照計画を手で持つと、手間は「スタイル数 × 計画の型の変更回数」で増える（fb の参照計画だけで430行）。
