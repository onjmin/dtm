# 旋律モデル（オフライン）

旋律の**並び順**を学習するモデル。ブラウザ向けの本体（TypeScript）には載せない。
オフラインで大量に生成し、**通ったものだけをデータとして同梱する**。

## なぜこれが要るのか

生成物と参考コーパスは `compare-corpus.ts` の17指標も、隣接音程のヒストグラムも
ほぼ一致している。反復はむしろ生成物の方が多い。それでも目隠しの聴取テストでは
**12/13 で人間と機械が分離する**。

分布が一致して知覚が分離するなら、差は分布ではなく**並び順**にある。距離を目標に
する方式（＝ルールと統計）ではこの情報は原理的に入らない。

`src/compose-phrases.ts`（人間の曲から抜き出した実在の2小節）は、並び順を作らずに
**借りる**ことでこれに対処している。このモデルはその次で、**借りる先を増やす**。

## 手順

### 0. データを出す（TypeScript 側）

```bash
npx tsx scripts/export-dataset.ts --dir <MIDIのフォルダ> --out tmp/dataset.jsonl
```

主旋律だけを JSONL で出す。トークン化はしない（何を1トークンにするかはモデルの
設計事項なので `tokenizer.py` に閉じ込める）。

### 1. 事前学習（大きなコーパス = PDMX）

```bash
# 取得（214MB）。中身は MIDI 254,035本
curl -L -o tmp/pdmx/mid.tar.gz "https://zenodo.org/records/15571083/files/mid.tar.gz?download=1"
tar -xzf tmp/pdmx/mid.tar.gz -C tmp/pdmx

npx tsx scripts/export-dataset.ts --dir tmp/pdmx/mid --out tmp/pdmx.jsonl
python tools/melody-model/train.py --data tmp/pdmx.jsonl --out tmp/base.pt --steps 60000
```

コーパスに **PDMX** を採る理由は `docs/dataset-provenance.md` にある（作風が界隈曲に
近いことを実測済み・パブリックドメイン申告・CC-BY で由来を書けば同梱できる）。
Lakh MIDI は配布元自身が帰属を辿れないと書いているので採らない。

**ここが B-1 の本体。** 界隈曲91本はトークン 99,238 個しかなく、これだけで学習すると
一般化ではなく**暗記**になる。暗記したモデルが出すのはコーパスの近似コピーで、それは
すでにある `compose-phrases.ts` とほぼ同じものにしかならない。

「91本には無い旋律の運び方」を入れるには、大きなコーパス（Lakh MIDI など）で
先に学習させる必要がある。`export-dataset.ts` は任意のフォルダを読めるので、
同じ手順で JSONL にできる。

**出自について。** 事前学習に他人の曲を使うと、**出力はそこに由来する**。同梱の
可否はプロジェクトの判断事項で、`export-dataset.ts` が各曲の `source` を残して
あるのは、あとから由来を辿れるようにするため。

**実測（2026-09-18）。** MIDI 254,035本 → 主旋律が取れた 186,774曲 / 音 3,689万 →
トークン 117,897,237。書き出しに23分、60,000ステップの学習に約2時間（RTX 4060 Ti）。
検証損失 0.479 で、学習側とほぼ同値。

### 2. 微調整（界隈曲91本）

```bash
python tools/melody-model/train.py --data tmp/dataset.jsonl --init tmp/base.pt \
    --out tmp/melody-model.pt --steps 600 --lr 1e-4 --eval-every 25
```

事前学習より **学習率を下げ、回数も減らす**。ここで長く回すと事前学習で得た
運び方が消えて、暗記へ戻る。検証損失が上がり始めたら止める（保存されるのは
最良の1つなので、回しすぎても結果は壊れない）。

**実測では 25ステップが最良**（検証 0.535）で、以降は上がる一方だった。91本は
事前学習の1/1000以下しかないので、最良点は既定の評価間隔（250）より手前に来る。
**`--eval-every` を刻まないと最良点を跨いでしまう。**

効きの内訳は、界隈曲の同じ検証データで
ゼロから学習 1.223 → 事前学習のみ 0.580 → 微調整後 0.535。
**差の大半は事前学習が作っている。**

### 3. 生成してバンクへ

```bash
python tools/melody-model/generate.py --model tmp/melody-model.pt \
    --out src/compose-melodies.ts --n 2000 --keep 801
```

**`--keep` が要る。** 2000本引くと候補は 19,969種・2.7MB になり、人間側のバンク
（801種・111KB）の24倍。ブラウザ向けの本体に入るものなので、同数へそろえる。

`src/compose-phrases.ts` と**同じ形**（2小節の `rhythm` / `degrees`）で出す。
生成側の配線をそのまま使えるので、実在フレーズとモデル製フレーズを差し替えて
同じ土俵で比べられる。曲まるごとを素材にするのは次の段階。

### 4. 耳で判定する（フレーズ単位ではなく、バンク単位で）

```bash
npx tsx tmp/ab-bank.ts --out tmp/ab-bank
```

**フレーズを1つずつ選ぶ方式は成立しない。** 以前ここには「耳で選ぶ／コストは1回きり」
と書いてあったが、実行可能性を確かめていなかった。2000本引くと候補は19,969種あり、
同梱ぶんを801種に絞っても、実測の聴取能力（**1回5本まで**。24本送って後半12本は
聴かれなかった）では160回の試聴になる。

さらに判断の形式そのものが無効で、**伴奏なしのメロディ単体では判断が難しい**ことが
同じ実測で分かっている（`docs/handover-compose.md`）。2小節の断片はもっと短い。

だから耳は**バンク2つの比較**に使う。`tmp/ab-bank.ts` が同じ曲を素材だけ入れ替えて
2本出す（`drawCount: 1` で引くので調・テンポ・構成・コード・ドラムまで一致し、
違いは旋律だけ）。サビ8小節・全トラック入り・目隠しで**5組10本・約3分**。

答えが出る問いは「**モデル製のバンクを採るか**」の1つ。801回の取捨には使わない。
フレーズ単位の絞り込みは `--keep`（`weight` 比例の抽出）が人手ゼロでやる。

**実測の結果（2026-09-19）: 差が無かった。** 5組10本で「どっちも似たようなもん」。
人間の曲から抜いた**本物の2小節**と、事前学習したモデル製の2小節が区別されない。

**2小節という単位に問題がある**、と読むべき結果。ここで出しているフレーズは、
モデルが学んだ並び順のうち**2小節を超えるぶんを捨てている**。詳細と次の一手は
`docs/handover-compose.md`。

## ファイル

| | |
|---|---|
| `tokenizer.py` | 旋律 ↔ トークン列。REMI風（BAR / POS / DEG / DUR）。単体実行で往復の検算ができる |
| `train.py` | 小さな decoder-only Transformer。`--init` で事前学習から再開 |
| `generate.py` | サンプリング → 2小節フレーズ → `src/compose-melodies.ts` |

## 注意

- `tools/` は npm パッケージに入らない（`package.json` の `files` は `dist` のみ）
- 語彙（`tokenizer.py` の `build_vocab`）の**順番を変えると学習済みモデルと食い違う**。
  足すときは末尾へ
- 度数は曲ごとに7の倍数でずらして ±21 の窓へ収めている（`octave_offset`）。
  7の倍数なのは音階上の位置を保つため。どのオクターブで歌うかは音符列の性質では
  なく声域の話で、生成側の `Register` が別に決める
